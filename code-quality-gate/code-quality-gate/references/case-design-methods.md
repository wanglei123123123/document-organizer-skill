# 用例设计方法扩展（Case Design Methods Extension）

> 本文是对 `test-methods.md` 的扩展，专门定义两种**结构化的用例设计方法**：
>
> - **判定表法（Decision Table Testing）** — 多条件组合下系统输出的全覆盖
> - **状态转换测试（State Transition Testing）** — 状态机所有状态/有效路径/循环路径的覆盖
>
> 这两类方法适用于：登录态切换、下载安装状态机、订单流程、权限组合、表单校验等典型业务。

---

## 一、判定表法（Decision Table Testing）

### 1.1 方法定义

判定表是一种**精确而紧凑的方式**，用来描述**多个输入条件（Conditions）与多个输出动作（Actions）之间的逻辑组合关系**。
通过把"条件 → 动作"映射成表格，强制穷举所有组合，避免遗漏。

**适用场景**：
- 业务规则由 ≥ 2 个条件共同决定输出（如：是会员 + 已登录 + 当日未领奖 → 可领奖）
- 不同条件组合产生不同动作（如：金额×支付方式×优惠类型 → 不同的折扣策略）
- 因果图法分析复杂时，用判定表更清晰

### 1.2 判定表结构

```
┌──────────────────────┬───────────┬───────────┬───────────┬───────────┐
│                      │  规则 R1  │  规则 R2  │  规则 R3  │  规则 R4  │
├──────────────────────┼───────────┼───────────┼───────────┼───────────┤
│ 条件桩 (Conditions)  │           │           │           │           │
│  C1: 是否登录         │     T     │     T     │     F     │     F     │
│  C2: 是否会员         │     T     │     F     │     T     │     F     │
│  C3: 是否首次领奖     │     T     │     T     │     T     │     T     │
├──────────────────────┼───────────┼───────────┼───────────┼───────────┤
│ 动作桩 (Actions)     │           │           │           │           │
│  A1: 直接发奖         │     ✓     │           │           │           │
│  A2: 提示开通会员     │           │     ✓     │           │           │
│  A3: 跳转登录         │           │           │     ✓     │     ✓     │
└──────────────────────┴───────────┴───────────┴───────────┴───────────┘
```

**四要素**：
| 要素 | 含义 |
|------|------|
| **条件桩** | 所有输入条件，每个取值有限（通常布尔 T/F，也可以是枚举） |
| **条件项** | 每条规则下条件的具体取值组合 |
| **动作桩** | 系统所有可能的输出动作 |
| **动作项** | 每条规则下被触发的动作 |

### 1.3 判定表设计五步法

```
Step 1 → 列出所有条件 (Cn)
Step 2 → 列出所有动作 (Am)
Step 3 → 计算规则总数：每个条件取值数相乘（n 个布尔条件 → 2^n 条规则）
Step 4 → 填表：对每条规则确定触发哪些动作
Step 5 → 化简（合并/删除冗余）→ 一条规则一条用例
```

### 1.4 判定表化简规则

| 化简方式 | 说明 |
|----------|------|
| **合并规则** | 若两条规则只有 1 个条件取值不同，但动作相同 → 该条件设为 "—"（不关心），合并为 1 条 |
| **删除不可能** | 业务上不可能的条件组合（如"未登录 + 已是会员"）→ 删除 |
| **拆分动作冲突** | 同一规则触发互斥动作 → 分析需求是否定义不清 |

**化简前后对比示例**：

```
化简前 (8 条规则):                    化简后 (5 条规则):
┌────┬────┬────┬────┐                ┌────┬────┬────┬────┐
│ R1 │ T  │ T  │ T  │ → A1            │ R1 │ T  │ T  │ T  │ → A1
│ R2 │ T  │ T  │ F  │ → A1  ┐         │ R2 │ T  │ T  │ F  │ → A1
│ R3 │ T  │ F  │ T  │ → A2  │ 合并    │ R3 │ T  │ F  │ —  │ → A2  ← C3不关心
│ R4 │ T  │ F  │ F  │ → A2  ┘         │ R4 │ F  │ —  │ —  │ → A3  ← C2/C3不关心
│ R5 │ F  │ T  │ T  │ → A3  ┐         └────┴────┴────┴────┘
│ R6 │ F  │ T  │ F  │ → A3  │ 合并
│ R7 │ F  │ F  │ T  │ → A3  │ (删: F+T不可能)
│ R8 │ F  │ F  │ F  │ → A3  ┘
└────┴────┴────┴────┘
```

### 1.5 用例覆盖准则

| 覆盖等级 | 要求 | 用例数 | 适用场景 |
|----------|------|--------|----------|
| **L1 每个条件取值至少出现一次** | 弱覆盖 | 取条件最多取值数 | 简单业务 |
| **L2 每条独立规则各出一条用例** | 标准覆盖 ⭐ | 化简后规则数 | 默认推荐 |
| **L3 全条件组合覆盖** | 最强 | 2^n / Π(取值数) | 高风险（支付/权限） |

**强制要求**：判定表必须给出 L2 级别覆盖，每条规则对应至少 1 条测试用例。

### 1.6 判定表→测试用例映射模板

```markdown
### TC-{模块}-DT-{规则号}: {动作描述}

- 优先级: P0/P1
- 测试方法: 判定表法 - 规则 R{n}
- 关联判定表: {判定表ID/名称}

| 条件 | 取值 |
|------|------|
| C1: 是否登录 | T |
| C2: 是否会员 | F |
| C3: 是否首次领奖 | T |

- 前置条件(Given): 已使用QQ账号登录(C1=T) + 账号未开通会员(C2=F) + 今日尚未领取(C3=T)
- 操作步骤(When):
  | 步骤 | 操作 | 预期 |
  |------|------|------|
  | 1 | 点击"领取奖励"按钮 | 弹出"开通会员"引导弹窗(对应动作 A2) |
- 动作映射: A2 提示开通会员
```

### 1.7 完整示例：应用宝下载操作判定表

**业务规则**：
- C1: 用户是否登录 (T/F)
- C2: 应用是否已下载 (T/F)
- C3: 网络是否可用 (T/F)
- 动作：A1=开始下载 / A2=显示"打开" / A3=登录引导 / A4=网络异常提示

**完整判定表**：

| 规则 | C1登录 | C2已下载 | C3网络 | 动作 |
|------|--------|----------|--------|------|
| R1 | T | T | — | A2 显示"打开" |
| R2 | T | F | T | A1 开始下载 |
| R3 | T | F | F | A4 网络异常提示 |
| R4 | F | — | — | A3 登录引导 |

→ 4 条用例（化简后）覆盖全部业务规则。

## 二、状态转换测试（State Transition Testing）

### 2.1 方法定义

把被测系统建模为**有限状态机（FSM）**：
- **状态（State）**：系统在某时刻的稳定状态（如"未下载"、"下载中"、"已暂停"）
- **事件（Event）**：触发状态改变的输入（如"点击下载"、"网络断开"）
- **转换（Transition）**：状态 + 事件 → 新状态 + 动作
- **初始状态/终止状态**：状态机的起点和终点

通过覆盖所有状态、所有有效转换、所有循环路径，验证系统在任意状态下接收任意事件都能正确响应。

**适用场景**：
- 下载/安装流程（典型！本 Skill 已在 test-methods.md 维度7 提供状态机图）
- 订单生命周期（待支付→已支付→发货中→已收货→已评价）
- 登录态流转（游客→登录中→已登录→Token过期→已登录/被踢下线）
- 文件/任务状态（草稿→待审核→已发布→已下架）
- 设备/连接状态（断开→连接中→已连接→重连中）

### 2.2 状态机建模四要素

```
┌──────────────────────────────────────────────────────────┐
│   状态机模型                                              │
├──────────────────────────────────────────────────────────┤
│                                                          │
│       事件E1                  事件E2                      │
│   ┌──────────┐             ┌──────────┐                 │
│   │  状态S1  │─── 动作A1 ──▶│  状态S2  │                 │
│   └──────────┘             └──────────┘                 │
│        ▲                        │                        │
│        │                        │ 事件E3                 │
│        │       事件E4           ▼                        │
│        └────────────────── ┌──────────┐                 │
│                            │  状态S3  │                 │
│                            └──────────┘                 │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

**四要素清单**：
| 要素 | 必须列出 |
|------|----------|
| **状态集合 S** | 所有合法状态（含初始/终止/异常态） |
| **事件集合 E** | 所有可能的输入/触发 |
| **转换函数 δ** | δ(s, e) → (s', a) 状态+事件如何过渡 |
| **初始/终止状态** | 系统起点和可接受的终点 |

### 2.3 状态转换表（State Transition Table）

> 把状态机展平为表格，**强制为每个状态下的每个事件指定行为**（包括"非法事件"也要明确）。

| 当前状态↓ \ 事件→ | 点击下载 | 暂停 | 继续 | 网络断开 | 完成回调 | 杀进程 |
|------------------|----------|------|------|----------|----------|--------|
| 未下载 | →下载中 / 创建任务 | 忽略 | 忽略 | 忽略 | 忽略 | 保持 |
| 下载中 | 忽略 | →已暂停 | 忽略 | →下载中(自动暂停态) | →下载完成 | 保持任务 |
| 已暂停 | 忽略 | 忽略 | →下载中 / 续传 | 忽略 | 忽略 | 保持任务 |
| 下载失败 | →下载中 / 重试 | 忽略 | →下载中 / 重试 | 忽略 | 忽略 | 保持 |
| 下载完成 | →安装中 | 忽略 | 忽略 | 忽略 | 忽略 | 保持 |

**关键检查点**：每个单元格必须明确标注以下三种之一：
- **→新状态 / 动作** — 合法转换
- **忽略** — 非法事件，应被拒绝且不影响状态
- **保持** — 状态不变，但触发副作用

### 2.4 五级路径覆盖准则（必读 ⭐）

> 状态转换测试有 5 个递增的覆盖等级，本 Skill 强制要求至少达到 **L3 全状态 + 全转换覆盖**。

| 等级 | 名称 | 覆盖目标 | 用例数 |
|------|------|----------|--------|
| **L0** | 状态覆盖 | 每个状态至少进入一次 | ≥ |S| |
| **L1** | 单转换覆盖（0-switch） | 每条合法转换至少触发一次 | = 转换数 |
| **L2** | 双转换覆盖（1-switch） | 每两条相邻转换组合至少触发一次 | = 转换对数 |
| **L3** | **全状态 + 全有效路径** ⭐ | 从初始态到每个终止态的所有简单路径全覆盖 | 路径数 |
| **L4** | **循环路径覆盖** ⭐ | 状态机中所有循环（cycle）至少执行一次 | 循环数 |
| **L5** | N-switch 完整覆盖 | 任意 N 条连续转换的所有组合 | 组合爆炸 |

**强制要求（用例评审硬指标）**：
- ✅ **L0 状态覆盖** — 必须 100%
- ✅ **L1 单转换覆盖** — 必须 100%（含合法 + 非法事件拒绝）
- ✅ **L3 全有效路径** — 必须 100%
- ✅ **L4 循环路径** — 必须 100%（每个 cycle 至少跑一次）
- ⚠️ **L2 双转换** — 建议 ≥ 80%
- ⚪ **L5** — 仅高安全级别业务（支付/账号）

### 2.5 路径识别算法（如何找出所有路径和循环）

```
┌──────────────────────────────────────────────────────────┐
│  Step 1 — 列出所有状态 S = {s1, s2, ..., sn}              │
│  Step 2 — 列出所有转换 T = {(si, e, sj, action)}         │
│  Step 3 — 用图论方法：                                    │
│           ① DFS 遍历从初始态可达的所有状态 → 状态覆盖     │
│           ② 标记每条边访问过 → 单转换覆盖                  │
│           ③ 找出所有从初始态到终止态的简单路径 → L3       │
│              （简单路径 = 不重复经过同一节点）             │
│           ④ 用 Tarjan / Johnson 算法找强连通分量          │
│              中的环路 → L4 循环                           │
│  Step 4 — 每条路径/循环 → 1 条测试用例                    │
└──────────────────────────────────────────────────────────┘
```

**简化经验法则**（无需实际跑算法）：
- 把状态图画出来，用红笔标记每条转换
- 从初始态出发，画出所有终止可达的"主路径"
- 重点找出**自循环**（s→s）、**短循环**（s1→s2→s1）、**长循环**（s1→s2→s3→s1）
- 每个循环必须设计至少一条用例：进入循环 → 循环 1 次 → 循环 N 次 → 退出循环

### 2.6 完整示例：下载状态机的状态转换测试

**已在 `test-methods.md 维度7` 中给出状态机图**，以下为完整路径分解：

#### 状态集合
```

```

|--------|----------|----------|
| P-01 | 未下载→下载中→下载完成→安装中→已安装 | 标准下载安装成功路径 |
| P-02 | 未下载→下载中→已暂停→下载中→下载完成→安装中→已安装 | 下载暂停继续后完成 |
| P-03 | 未下载→下载中→下载失败→下载中→下载完成→安装中→已安装 | 下载失败重试后成功 |
| P-04 | 未下载→下载中→下载完成→安装中→安装失败→安装中→已安装 | 安装失败重试后成功 |

| 循环ID | 循环序列 | 用例标题 |
|--------|----------|----------|

| L-02 | 下载中⇄下载失败（失败重试） | 多次失败重试 |

| 状态 | 非法事件 | 预期行为 |
|------|----------|----------|
| 未下载 | 暂停/继续 | 按钮不可见或点击无效 |
| 已暂停 | 再次暂停 | 忽略 |
| 已安装 | 重新下载 | 触发更新检查或保持已安装态 |
| 下载完成 | 暂停 | 不可暂停（已下载完） |

### 2.8 状态转换测试 Checklist

设计完后必须自检：

- [ ] 是否列出了所有状态（含初始/终止/异常态）？
- [ ] 是否绘制了状态转换图？
- [ ] 是否列出了状态转换表（每个状态×每个事件）？
- [ ] **L0 状态覆盖**：每个状态至少 1 条用例进入？
- [ ] **L1 单转换覆盖**：每条合法转换至少 1 条用例？
- [ ] **L1 非法事件**：每个状态下的非法事件至少 1 条拒绝用例？
- [ ] **L3 有效路径**：从初始态到每个终止态的所有简单路径都有用例？
- [ ] **L4 循环路径**：每个循环至少 1 条用例（含进入/循环N次/退出）？
- [ ] 异常打断：每条路径中"杀进程/断网/切账号"是否打断后状态可恢复？
- [ ] 状态持久化：杀进程/重启后状态是否能从持久化中正确恢复？

## 三、场景法（Scenario-based Testing，基本流 + 备选流 + 数据驱动）

### 3.1 方法定义

场景法以**用户视角**出发，把一个用例划分成一个或多个"业务场景"，每个场景由：
- **基本流（Basic Flow）**：用户按预期路径走完业务的**最理想**路径
- **备选流（Alternate Flow）**：在基本流某个节点上分叉出去的**替代路径**（可能成功、可能失败、可能回到基本流、可能直接终止）

配合 **数据驱动（Data-Driven）** 思想：同一场景结构，改变驱动数据 → 自动衍生一批等价用例，降低重复劳动。

**核心观点**：
> 场景法 ≠ 把所有功能点堆一起。
> 场景法 = 用户故事 + 路径分叉 + 数据驱动表

**适用场景**：
- 端到端（E2E）业务流程（如：注册 → 登录 → 搜索 → 下载 → 安装 → 打开）
- 涉及多步骤用户交互的功能（支付、发帖、下单）
- 与状态转换测试结合使用（状态机负责状态合法性，场景法负责用户体验）
- 涉及不同用户角色、不同数据组合的业务

### 3.2 基本流与备选流建模

```
┌──────────────────────────────────────────────────────────┐
│                场景法路径模型                             │
├──────────────────────────────────────────────────────────┤
│                                                          │
│   起点                                                   │
│    ●                                                     │
│    │                                                     │
```

### 3.3 场景法五要素

| 要素 | 含义 | 示例 |
|------|------|------|
| **Actor** | 执行场景的角色 | 新用户 / 老用户 / VIP / 游客 |
| **Goal** | 用户想达到的目标 | 成功下载一个APP |
| **Precondition** | 进入场景前的状态 | 已打开应用宝，已登录 |
| **Basic Flow** | 理想路径（无异常无打断） | 搜索→点下载→等待→安装完成→打开 |
| **Alternate Flows** | 所有分叉路径 | 搜索无结果 / 网络异常 / 存储不足 / ... |
| **Postcondition** | 场景结束后的状态 | 应用已成功打开 |

### 3.4 备选流四类分类

> 备选流是漏测高发区，必须系统化列举。按业务含义分四类：

| 类型 | 说明 | 典型示例 | 是否回流 |
|------|------|----------|----------|
| **A 成功替代** | 不同方式达成同一目标 | 密码登录 vs 验证码登录 vs 扫码登录 | 回流到基本流 |
| **B 失败可恢复** | 出错后可重试继续 | 密码错误 / 验证码超时 / 网络瞬断 | 回流到前一节点 |
| **C 失败终止** | 出错后无法继续，退出场景 | 账号封禁 / 服务不可用 / 用户取消 | 终止 |
| **D 并行分支** | 在某节点触发独立子流程 | 下载中切换账号 / 安装中收到通知 | 回流到基本流 |

**场景穷举模板**：
```
对每一个基本流节点 Ni，逐一问：
  Q1: 用户在 Ni 上除了"走下一步"，还能做什么？  → A 成功替代
  Q2: Ni 可能出什么错？出错后能重试吗？          → B 失败可恢复
  Q3: Ni 可能出什么致命错？必须终止场景？        → C 失败终止
  Q4: 在 Ni 执行期间，外部可能打断吗？           → D 并行分支
```

### 3.5 数据驱动：场景结构 × 数据集 = 用例矩阵

#### 3.5.1 数据驱动核心思想

```
场景法（结构）               数据表（变量）
─────────────              ─────────────
Given {X}, When do {Y}      | X=?  | Y=?  | Z=? | 预期 |
 → Then {Z}                 |------|------|-----|------|
                           → | A    | M    | P   | ...  |
                             | B    | N    | Q   | ...  |
                             | ...  | ...  | ... | ...  |

每行数据 → 衍生 1 条测试用例
```

**数据驱动的三种实现方式**：

| 实现形式 | 说明 | 适用 |
|----------|------|------|
| **数据参数化表格** | 同一场景结构，用表格列驱动数据变化 | 用例编写/评审阶段 |
| **Gherkin Scenario Outline** | 使用 `Examples:` 数据段 | BDD 框架（Cucumber/Behave） |
| **代码 @parametrize** | 单元/接口测试的参数化 | 自动化测试脚本 |

#### 3.5.2 数据维度挑选（MECE 原则）

数据集必须**互斥且完备**（Mutually Exclusive, Collectively Exhaustive）：

| 维度 | 挑选方法 | 规则依据 |
|------|----------|----------|
| **等价类数据** | 有效类 1 个代表 + 无效类每类 1 个 | 等价类划分法 |
| **边界数据** | 最小/最大/超限/空/特殊字符 | 边界值分析法 |
| **用户分群数据** | 新/老/VIP/游客 | `boundary-techniques.md` 维度6 |
| **账号体系数据** | QQ / 微信 / 未登录 | `boundary-techniques.md` 维度6 |
| **环境数据** | Wi-Fi / 弱网 / 断网 | 弱网测试 |
| **时间数据** | 正常 / 过期 / 跨零点 / 时区边界 | 边界值维度3 |

### 3.6 用户体验（UX）驱动的场景设计原则

场景法的核心是"从用户视角设计"，以下六条原则来自真实 UX 体验。

| # | 原则 | 说明 | 反例 vs 正例 |
|---|------|------|-------------|
| **UX-1** | **完整旅程** | 从进入→达成目标→退出闭环，不能只测一个步骤 | ❌ 只测"输入"；✅ 测"进入→输入→提交→结果→返回" |
| **UX-2** | **用户视角** | 用"我要下载一个APP"而不是"调用download接口" | ❌ "调接口返回200"；✅ "用户看到下载进度条" |
| **UX-3** | **多角色覆盖** | 不同 Actor 在同一场景可能行为完全不同 | ❌ 只测QQ登录；✅ QQ / 微信 / 游客 三套 |
| **UX-4** | **真实数据** | 测试数据来自线上真实分布，避免纯编造 | ❌ `"abc"` ；✅ `"王者荣耀"`（线上TOP10应用） |
| **UX-5** | **多通道** | 不同入口/触达方式需分别覆盖 | ❌ 只测首页入口；✅ 首页 / 搜索 / 详情页 / 分享链接 |
| **UX-6** | **异常情绪** | 用户在异常场景下的情绪处理（友好提示/可恢复） | ❌ 只展示"error"；✅ "网络不佳，请重试"+重试按钮 |

### 3.7 场景法覆盖准则

场景法有四级递增覆盖，本 Skill **强制要求 L2 基本流 + 备选流全覆盖**。

| 等级 | 覆盖目标 | 用例数 |
|------|----------|--------|
| **L0 基本流** | 只覆盖最理想路径 | 1 条 |
| **L1 基本流 + 主要备选流** | 基本流 + 高频备选（通常3~5条） | 4~6 条 |
| **L2 基本流 + 全备选流** ⭐ | 基本流 + 所有 A/B/C/D 类备选流 | 基本流1 + 备选流 N |
| **L3 L2 + 数据驱动组合** | 每条流再用数据集衍生 | L2 × 数据行数 |

**强制要求**：
- ✅ L0 基本流 — 必测 1 条 P0
- ✅ L1 主要备选流 — 至少 3 条（A/B/C 各至少 1 条）
- ✅ **L2 全备选流** — 必测（识别出所有 A/B/C/D 类备选流）
- ⚠️ L3 数据驱动 — 建议（核心业务必须，长尾业务可选）

### 3.8 场景法 vs 状态转换测试：何时选择

| 区别 | 场景法 | 状态转换测试 |
|------|--------|--------------|
| **视角** | 用户视角（我想做什么） | 系统视角（系统处于什么状态） |
| **粒度** | 业务端到端（多步骤） | 状态×事件单步 |
| **关注点** | 路径正确性 + 用户体验 | 状态转换正确性 + 非法事件拒绝 |
| **输出** | 基本流 + 备选流 + 数据表 | 状态机图 + 转换表 + 路径列表 |
| **适用** | 业务流程 / 端到端测试 | 流程性状态机 / 有明确状态集 |
| **联用** | 场景法铺基本路径 + 状态转换覆盖每状态×事件的非法事件 | |

**联用示例**：
- 下载安装场景：用**场景法**写"从搜索→下载→打开"的 5 条基本备选流；用**状态转换测试**验证"下载中收到暂停/继续/失败等 15 种事件"的状态正确性。

## 四、判定表 vs 状态转换 vs 场景法 vs 因果图：何时用哪个？

```
┌────────────────────────────────────────────────────────┐
│              四种结构化方法对比                          │
├────────────────────────────────────────────────────────┤
│                                                        │
│  是"用户业务流程/端到端测试"?                            │
│   └─ Yes → 场景法                                      │
│            (基本流 + 备选流 + 数据驱动)                 │
│                                                        │
│  系统是"有状态/流程性"?                                  │
│   └─ Yes → 状态转换测试                                 │
│            (当前状态 + 事件 → 新状态 + 动作)             │
│                                                        │
│  系统是"无状态/单次决策"?                                │
│   └─ Yes → 判定表法                                    │
│            (输入条件×组合 → 输出动作)                   │
│                                                        │
│  条件之间有"因果/约束依赖"?                              │
│   └─ Yes → 因果图法                                    │
│            (因 → 果，含强制/必须/排他/包含等约束)       │
│                                                        │
└────────────────────────────────────────────────────────┘
```

| 方法 | 强调点 | 输出形式 | 典型场景 |
|------|--------|----------|----------|
| **场景法** | 用户旅程 + 路径分叉 | 基本流图 + 备选流清单 + 数据驱动表 | 端到端业务、注册登录、下载安装、下单支付 |
| **判定表法** | 条件组合的完整性 | 表格（行=规则） | 权限校验、价格规则、表单业务规则 |
| **状态转换测试** | 流程的合法性与稳健性 | 状态图+转换表+路径列表 | 下载、订单、登录态、设备连接 |
| **因果图法** | 条件之间的逻辑约束 | 因果图（与/或/非/约束） | 复杂校验规则、互斥/包含约束 |

**联用建议**：
- **端到端业务** = 场景法主导（基本流+备选流） + 状态转换（每个流程节点的状态合法性）
- 复杂业务规则 = 因果图（梳理约束）→ 判定表（穷举组合）→ 用例
- 流程性业务 = 状态转换测试（主线）+ 判定表（每个状态下的决策）
- **数据驱动** 可叠加到任一方法上：每条规则/状态路径/场景都可配数据表衍生

## 六、常见漏测模式（基于经验）

| # | 漏测场景 | 高发原因 | 强制对应规则 |
|---|----------|----------|--------------|
| 1 | 判定表只覆盖了正向规则，未覆盖反向 | 默认"未触发动作"=正常 | 判定表 L2 标准覆盖 |
| 2 | 不可能组合未删除，造成测试浪费 | 未做化简 | 1.4 化简规则 |
| 3 | 状态机只测了"主路径"，循环未测 | 不知道存在循环 | L4 循环路径 |
| 4 | 非法事件未测（如已安装时再下载） | 关注"happy path" | L1 非法事件覆盖 |
| 5 | 异常打断后状态不能恢复 | 未测"杀进程→重启" | 2.8 Checklist |
| 6 | 多级状态嵌套时（如下载中+登录态切换）漏测 | 单一维度建模 | 多维度状态机 |
| 7 | 跨账号/跨设备状态隔离漏测 | 单账号测试惯性 | 状态持久化 |
| 8 | **场景法只写基本流，没识别备选流** | 关注"happy path" | 3.7 L2 全备选流覆盖 |
| 9 | **备选流只覆盖了 B 类失败，漏 A/C/D** | 分类不系统 | 3.4 备选流四类 |
| 10 | **单条用例堆多角色数据，无法定位问题** | 未用数据驱动 | 3.5 数据驱动表 |
| 11 | **数据集都是编造的，不反映线上真实分布** | 数据来源单一 | UX-4 真实数据 |
| 12 | **只测一个入口，漏了分享/扫码/深链等其他通道** | 单通道思维 | UX-5 多通道覆盖 |
