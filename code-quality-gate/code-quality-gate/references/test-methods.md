> 本文件定义经典软件测试方法的原理、规则化映射方式及代码级检测点。

## 一、边界值分析法 (Boundary Value Analysis)

### 1.1 方法原理

边界值分析是一种黑盒测试方法，基于"错误更容易发生在输入/输出的边界上"这一经验法则。程序在处理边界条件时最容易出现问题。

### 1.2 边界类型分类

> **核心原则**: 边界不仅是数值上下限,更包括**类型互斥边界、用户身份边界、操作路径边界、
> 环境/状态边界**等业务语义层面的边界。漏测往往发生在"只考虑了目标类型,没有考虑非目标类型"。

```
┌─────────────────────────────────────────────────────────────────┐
│                   边界类型全景 (六维度模型)                       │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  维度1: 数值边界 (技术层)                                       │
│  ├── 上确界 (max)         例: int最大值、数组长度上限            │
│  ├── 下确界 (min)         例: int最小值、负数边界                │
│  ├── 上边界外 (max+1)     例: 溢出场景                           │
│  ├── 下边界外 (min-1)     例: 下溢场景                           │
│  └── 零值/空值           例: 0、null、""                        │
│                                                                 │
│  维度2: 序列/集合边界 (技术层)                                   │
│  ├── 空集合               例: 空列表、空Map                      │
│  ├── 单元素集合           例: 只有1个元素的列表                   │
│  ├── 最大容量集合         例: 满容量的缓冲区                      │
│  └── 超容量集合           例: 超过最大长度的字符串                 │
│                                                                 │
│  维度3: 时间边界 (技术层)                                       │
│  ├── 时间戳边界           例: Unix时间戳极值、闰秒                │
│  ├── 时区切换边界         例: 夏令时切换、跨日/跨月               │
│  └── 并发时间窗口         例: TTL过期临界、超时边界               │
│                                                                 │

│  │  频控模型: "在时间窗口T内, 最多触发N次, 超限后抑制"            │
│  │                                                               │
│  │  ┌─── 时间窗口边界 ───┐                                      │
│  │  ├── 窗口起始点 (T=0)                                        │
│  │  │   例: 弹窗频控"每天最多3次" → 0点整重置? 还是滑动24h?     │
│  │  ├── 窗口内 (0 < t < T)                                     │
│  │  │   ├── 窗口内未达上限 → 应正常触发                         │
│  │  │   ├── 窗口内恰好=上限 → 本次是否触发? 边界!               │
│  │  │   └── 窗口内超过上限 → 应被抑制,但UI给什么反馈?           │
│  │  ├── 窗口结束点 (t=T)                                       │
│  │  │   例: 恰好在窗口到期的瞬间触发 → 算旧窗口还是新窗口?      │
│  │  ├── 窗口刚过 (t=T+1)                                      │
│  │  │   例: 窗口过期后第一次触发 → 计数是否正确重置?            │
│  │  └── 跨窗口连续操作                                          │
│  │      例: 窗口末尾触发2次 + 新窗口开始立即触发1次              │

│  │                                                               │
│  │  ┌─── 次数边界 ───┐                                          │
│  │  ├── 第0次 (从未触发过)                                      │
│  │  │   例: 首次打开APP弹窗? 还是需要某个前置条件?              │
│  │  ├── 第1次 ~ 第(N-1)次 (未达限制)                            │
│  │  │   例: 每次触发后计数器是否正确+1?                         │
│  │  ├── 第N次 = 恰好达到上限                                    │
│  │  │   例: 频控3次, 第3次弹 → 弹了之后是否立即停止?           │
│  │  │   还是第3次就不弹? (含第3次 vs 不含第3次 = off-by-one!)  │
│  │  ├── 第N+1次 = 超过上限                                     │
│  │  │   例: 第4次请求弹窗 → 不弹, 但后续逻辑是否受影响?        │
│  │  └── 重置后第1次                                              │
│  │      例: 窗口过期/手动重置/清缓存后 → 计数是否真正归零?      │
│  │                                                               │
│  │  ┌─── 频控组合/叠加边界 ───┐                                  │
│  │  ├── 多级频控叠加                                             │
│  │  │   例: "每小时最多2次 AND 每天最多5次"                     │
│  │  │   → 小时窗口重置了但日窗口没重置, 能弹吗?                │
│  │  ├── 多场景共享频控池                                         │
│  │  │   例: A弹窗和B弹窗共享"每天弹窗总次数≤5"                 │
│  │  │   → A弹了3次后,B最多只能弹2次                            │
│  │  ├── 频控跨设备/跨端                                         │
│  │  │   例: 手机端弹了3次, 平板端也受限? 还是独立计数?          │
│  │  ├── 频控与登录态关系                                         │
│  │  │   例: 未登录时弹了2次, 登录后重新计数? 还是延续?          │
│  │  │   例: QQ登录弹了3次, 切换微信登录 → 重新计数?             │
│  │  └── 频控持久化与清除                                         │
│  │      例: 频控计数存在哪里? 本地缓存/服务端/Cookie?           │
│  │      例: 清除APP缓存后计数清零? 卸载重装后呢?               │
│  │      例: 服务端下发了新的频控策略 → 已有计数怎么处理?        │
│  │                                                               │
│  │  ┌─── 频控时间语义歧义 ───┐                                   │
│  │  ├── "每天" = 自然日(0:00~24:00) or 滑动24小时?              │
│  │  ├── "每周" = 自然周(周一~周日) or 滑动7天?                  │
│  │  ├── "每次启动" = 冷启动? 热启动(从后台回来)也算?           │
│  │  ├── "每次进入页面" = 页面首次渲染? 每次可见(含切回)?       │
│  │  └── "间隔N秒" = 从展示开始计? 从关闭开始计? 从请求开始计?  │
│  │                                                               │
│  │  【频控典型边界测试用例清单】                                  │
```

#### RULE-BV-01: 数值范围校验存在性
```yaml
规则ID: RULE-BV-01
名称: "数值范围校验存在性"
测试方法: 边界值分析
严重程度: BLOCKER
检测目标: 所有接收数值参数的函数/方法
检测逻辑: 
  - 识别函数签名中的数值型参数(int, float, long, double, number等)
  - 检查函数体内部是否存在对该参数的范围校验(>=, <=, >, <, Math.min/max, clamp等)
  - 若无任何范围校验且该参数用于后续计算/存储/网络传输 → 报告问题
误报抑制:
  - 私有辅助函数且调用方已校验
  - 参数由枚举/常量限定
  - 语言层面有类型保护(如TypeScript的类型字面量)
示例:
  ❌ Bad:
    def calculate_discount(price):
        return price * 0.9  # 无边界校验
    
  ✅ Good:
    def calculate_discount(price):
        if price <= 0 or price > MAX_PRICE:
            raise ValueError("Invalid price")
        return price * 0.9
```

## 二、等价类划分法 (Equivalence Partitioning)

### 2.1 方法原理

将所有可能的输入数据划分为若干个等价类，每个等价类中的数据对于揭露错误来说是等效的。从每个等价类中选取代表性数据进行测试，可以用较少的用例达到较好的覆盖效果。

### 2.2 等价类划分策略

```
┌──────────────────────────────────────────┐
│           等价类划分模板                   │
├──────────────────────────────────────────┤
│                                          │
│  输入条件: 年龄 (age)                    │
│                                          │
│  有效等价类:                             │
│  ├── EP1: 18 ≤ age ≤ 60  (正常成年用户)  │
│  └── EP2: 60 < age ≤ 100 (老年用户)      │
│                                          │
│  无效等价类:                             │
│  ├── IEP1: age < 0        (负数)         │
│  ├── IEP2: age = 0        (零岁)         │
│  ├── IEP3: 0 < age < 18   (未成年)       │
│  └── IEP4: age > 100      (超高龄)       │
│                                          │
│  选取测试用例: 每个等价类选1个代表值      │
│                                          │
└──────────────────────────────────────────┘
```

### 2.3 代码级检测规则

#### RULE-EP-01: 输入等价类覆盖完整性
```yaml
规则ID: RULE-EP-01
名称: "输入等价类覆盖完整性"
测试方法: 等价类划分
严重程度: BLOCKER
检测目标: 有明确业务规则的输入参数
检测逻辑:
  - 识别带有业务含义的参数(通过命名推断: status, type, role, mode等)
  - 检查代码是否对所有已知的有效等价类进行了处理
  - 检查是否对所有无效等价类进行了拒绝/异常处理
  - 若switch/if-else链中存在未处理的case/default → 报告
示例:
  ❌ Bad:
    def handle_order_status(status):
        if status == "pending":
            process_pending()
        elif status == "completed":
            process_completed()
        # 缺少: "cancelled", "refunded", 其他非法值的处理
    
  ✅ Good:
    def handle_order_status(status):
        valid_statuses = {"pending", "completed", "cancelled", "refunded"}
        if status not in valid_statuses:
            raise ValueError(f"Invalid status: {status}")
        
        handlers = {
            "pending": process_pending,
            "completed": process_completed,
            "cancelled": process_cancelled,
            "refunded": process_refunded,
        }
        handlers[status]()
```

#### RULE-EP-02: 枚举/状态完备性
```yaml
规则ID: RULE-EP-02
名称: "枚举/状态完备性检查"
测试方法: 等价类划分
严重程度: CRITICAL
检测目标: switch语句、if-elif-else链、模式匹配
检测逻辑:
  - 提取所有相关的枚举值/状态常量
  - 检查处理逻辑是否覆盖了所有枚举值
  - 对于switch: 是否有default分支
  - 对于if-elif: 最后是否有else兜底
示例:
  ❌ Bad (Java):
    switch(orderStatus) {
        case PENDING: handlePending(); break;
        case PAID: handlePaid(); break;
        // 缺少 default 和其他状态
    }
    
  ✅ Good (Java):
    switch(orderStatus) {
        case PENDING: handlePending(); break;
        case PAID: handlePaid(); break;
        case SHIPPED: handleShipped(); break;
        case DELIVERED: handleDelivered(); break;
        case CANCELLED: handleCancelled(); break;
        default: throw new IllegalArgumentException("Unknown status");
    }
```

```yaml
        return amount + tax
```

## 三、因果图法 (Cause-Effect Graphing)

### 3.1 方法原理

因果图法用于分析输入条件的各种组合与输出结果之间的对应关系。通过图形化方式描述输入（原因）和输出（结果）之间的逻辑关系，确保所有有意义的输入组合都被测试到。

### 3.2 因果关系符号

```
┌─────────────────────────────────────────────┐
│            因果图基本关系                      │
├─────────────────────────────────────────────┤
│                                             │
│   恒等:    c ──→ e      (c成立则e成立)      │
│   非:      c ──┐                               │
│              │ O ─→ e   (c成立则e不成立)      │
│   或:    ╱─ c1 ─╲                              │
│         ├─ c2 ─┼──→ e  (任一成立则e成立)      │
│         ╲─ c3 ─╱                               │
│   与:    c1 ─┬──→ e  (全部成立e才成立)        │
│          c2 ─┘                                 │
│                                             │
└─────────────────────────────────────────────┘
```

### 3.3 代码级检测规则

#### RULE-CE-01: 多条件组合覆盖
```yaml
规则ID: RULE-CE-01
名称: "多条件组合逻辑完整性"
测试方法: 因果图法
严重程度: CRITICAL
检测目标: 包含多个布尔条件组合的复杂判断逻辑
检测逻辑:
  - 识别包含 && / || / and / or 的复合条件表达式
  - 列出所有条件的真值表组合
  - 检查代码是否处理了关键组合场景
  - 特别关注: 全真、全假、混合边界
示例:
  场景: 用户权限判断
  条件: is_admin AND is_active AND not is_suspended
  
  需要覆盖的组合 (共8种,至少测试6种关键组合):
  ┌─────────┬─────────┬────────────┬────────┐
  │ admin   │ active  │ suspended  │ 结果   │
  ├─────────┼─────────┼────────────┼────────┤
  │   T     │   T     │     F      │ 允许 ✓ │
  │   T     │   F     │     F      │ 拒绝 ✓ │
  │   F     │   T     │     F      │ 拒绝 ✓ │
  │   T     │   T     │     T      │ 拒绝 ✓ │
  │   F     │   F     │     F      │ 拒绝 ✓ │
  │   ...更多组合...                      │
  └─────────┴─────────┴────────────┴────────┘
  
  ❌ Bad:
    if user.is_admin and user.is_active:  # 缺少suspended检查
        allow_access()
    
  ✅ Good:
    can_access = (
        user.is_admin 
        and user.is_active 
        and not user.is_suspended
    )
    if can_access:
        allow_access()
    else:
        log_access_denied(user.id, get_denial_reason(user))
```

#### RULE-CE-02: 短路求值副作用
```yaml
规则ID: RULE-CE-02
名称: "短路求值副作用检测"
测试方法: 因果图法
严重程度: MAJOR
检测目标: 包含函数调用的逻辑表达式
检测逻辑:
  - 检测 &&/||/and/or 表达式中是否有函数调用
  - 短路求值可能导致部分函数不被执行
  - 若被短路的函数有副作用(修改状态、发送事件等) → 报告
示例:
  ❌ Bad:
    if validate_user() and log_access():  # validate失败则log不会执行
        grant_access()
    
  ✅ Good:
    is_valid = validate_user()
    log_access()  # 独立执行，不受短路影响
    if is_valid:
        grant_access()
```

## 四、正交实验法 (Orthogonal Array Testing)

### 4.1 方法原理

当输入因素较多且每个因素有多个水平时，使用正交表来选择最具代表性的测试用例组合，以最小的用例数量达到最大的覆盖率。

### 4.2 适用场景

```
┌──────────────────────────────────────────────┐
│         正交实验法适用场景                      │
├──────────────────────────────────────────────┤
│                                              │
│  ✅ 适用:                                     │
│  ├── 配置项组合测试 (多配置参数的系统)          │
│  ├── 表单多字段组合验证                        │
│  ├── 兼容性测试 (浏览器×操作系统×分辨率)        │
│  ├── 国际化测试 (语言×地区×货币×时区)          │
│  └── A/B实验变体组合                           │
│                                              │
│  ❌ 不适用:                                   │
│  ├── 因素间有强依赖关系的情况                   │
│  ├── 因素数量很少(<3个)的情况                   │
│  └── 需要穷举所有组合的关键路径                 │
│                                              │
└──────────────────────────────────────────────┘
```

### 4.3 代码级检测规则

#### RULE-OA-01: 配置组合覆盖
```yaml
规则ID: RULE-OA-01
名称: "多配置项组合测试充分性"
测试方法: 正交实验法
严重程度: MAJOR
检测目标: 可配置模块、特性开关(Feature Flag)、多环境配置
检测逻辑:
  - 识别模块的所有可配置参数/Feature Flag
  - 统计配置组合总数
  - 检查测试是否使用了正交或其他抽样策略
  - 若配置数≥5且测试用例数<配置组合总数的20% → 建议
示例:
  模块有6个Feature Flag, 每个有on/off两个值
  全组合: 2^6 = 64 种
  正交表 L8(2^7): 只需 8 个用例即可覆盖两两组合
  
  ❌ 问题: 只测试了 all-on 和 all-off 两种
  
  ✅ 推荐: 使用正交表设计8个用例,覆盖任意两个Flag的组合
```

### 5.3 代码级检测规则

#### RULE-EG-01: 除零保护
```yaml
规则ID: RULE-EG-01
名称: "除法运算除零保护"
测试方法: 错误推测法
严重程度: BLOCKER
检测目标: 所有除法(/, //, %, div)运算
检测逻辑:
  - 识别所有除法运算表达式
  - 检查除数是否能确定非零
  - 若除数来自外部输入或变量且无前置零值检查 → 阻断
示例:
  ❌ Bad:
    avg = total / count
    
  ✅ Good:
    if count == 0:
        avg = 0
    else:
        avg = total / count
```

#### RULE-EG-02: 资源释放保证
```yaml
规则ID: RULE-EG-02
名称: "资源释放完整性检查"
测试方法: 错误推测法
严重程度: CRITICAL
检测目标: 文件操作、数据库连接、网络请求、锁获取
检测逻辑:
  - 识别资源打开/获取操作
  - 检查是否存在对应的关闭/释放操作
  - 检查是否使用了 try-finally/with/using 等安全模式
  - 检查异常路径上资源是否也能释放
示例:
  ❌ Bad:
    f = open("data.txt")
    data = f.read()
    process(data)  # 若process抛异常,f不会被关闭
    
  ✅ Good (Python):
    with open("data.txt") as f:
        data = f.read()
        process(data)  # 无论是否异常,f都会被关闭
    
  ✅ Good (Java):
    try (Connection conn = getConnection()) {
        conn.executeQuery(sql);
    }  // 自动关闭
```

#### RULE-EG-03: 并发安全
```yaml
规则ID: RULE-EG-03
名称: "并发安全性检查"
测试方法: 错误推测法
严重程度: CRITICAL
检测目标: 共享变量访问、单例模式、缓存操作
检测逻辑:
  - 检测共享可变变量的读写操作
  - 检查是否有同步机制(lock, mutex, synchronized等)
  - 检查原子操作是否线程安全
  - 检查双重检锁(Double-Check Locking)是否正确实现
示例:
  ❌ Bad:
    class Singleton:
        _instance = None
        
        @classmethod
        def get_instance(cls):
            if cls._instance is None:  # 非线程安全
                cls._instance = Singleton()
            return cls._instance
    
  ✅ Good:
    class Singleton:
        _instance = None
        _lock = threading.Lock()
        
        @classmethod
        def get_instance(cls):
            if cls._instance is None:
                with cls._lock:
                    if cls._instance is None:  # DCL
                        cls._instance = Singleton()
            return cls._instance
```

## 六、各方法综合使用指南

> **扩展方法**：除本文 5 大经典方法外，另在 `case-design-methods.md` 中专门定义了
> **场景法（Scenario-based Testing，基本流+备选流+数据驱动）**、
> **判定表法（Decision Table Testing）** 和 **状态转换测试（State Transition Testing）**
> 三种结构化用例设计方法，分别覆盖"端到端用户旅程"、"多条件组合决策"和"流程性状态机"
> 三类高频业务。

```
┌─────────────────────────────────────────────────────┐
│           测试方法选择决策树                          │
├─────────────────────────────────────────────────────┤
│                                                     │
│  开始                                               │
│    │                                                │
│    ▼                                                │
│  是"用户业务流程/端到端"? ──Yes──▶ 场景法            │
│    │ No                          (基本流+备选流+     │
│    │                              数据驱动)          │
│    ▼                                                │
│  系统是"流程性/有状态"? ──Yes──▶ 状态转换测试       │
│    │ No                          (含L0~L4路径覆盖)  │
│    ▼                                                │
```

### 组合策略建议

| 场景 | 主方法 | 辅助方法 | 说明 |
|------|--------|----------|------|
| 表单验证 | 等价类 + 边界值 | 错误推测 | 覆盖各类输入及其边界 |
| 权限控制 | 判定表 + 因果图 | 等价类 | 多条件组合全覆盖 |
| 价格/优惠规则 | 判定表 | 边界值 | 规则化简后逐条覆盖 |
| 配置系统 | 正交实验 + 边界值 | 错误推测 | 大幅减少用例数量 |
| 计算引擎 | 边界值 + 错误推测 | 因果图 | 关注数值极端场景 |
| API接口 | 等价类 + 边界值 + 错误推测 | 判定表 | 三法联用最常见 |
| **端到端业务（注册/下单/下载）** | **场景法（基本流+备选流）** | 数据驱动 + 状态转换 | 用户旅程完整 + 备选流全覆盖 |
| 下载/安装/订单流程 | **状态转换测试** | 场景法 + 判定表 | L3全路径+L4循环必测 |
| 登录态/账号切换 | **状态转换测试** | 场景法（多角色数据驱动） | 含非法事件拒绝覆盖 |
| 设备/连接管理 | **状态转换测试** | 错误推测 | 重连/异常恢复路径 |
