### 2.3 按严重程度分级

| 等级 | 名称 | 定义 | 响应SLA | 示例 |
|------|------|------|---------|------|

## 三、根因分析方法 (Root Cause Analysis)

### 3.1 5Why分析法

**原理**: 连续问至少5次"为什么"，直到找到根本原因。

```
┌─────────────────────────────────────────────────────┐
│              5Why 分析实例                           │
├─────────────────────────────────────────────────────┤
│                                                     │
│  问题: 用户下单时偶尔出现订单金额为0                  │
│                                                     │
│  Why 1: 为什么金额为0?                              │
│  → 因为优惠券折扣计算后金额变成了负数，被强制设为0    │
│                                                     │
│  Why 2: 为什么允许折后金额为负?                      │
│  → 因为代码只检查了金额<0的情况，没检查优惠叠加       │
│                                                     │
│  Why 3: 为什么没有叠加校验?                          │
│  → 因为需求文档没有说明优惠券能否叠加使用             │
│                                                     │
│  Why 4: 为什么需求没有明确?                          │
│  → 因为产品经理假设"常识上不能叠加"，未写入需求       │
│                                                     │
│  Why 5: 为什么这种假设没有被验证?                    │
│  → 因为缺乏需求评审环节的技术挑战和用例反推           │
│                                                     │
│  ═════════════════════════════════════════          │
│  根因: 需求评审流程不完善，缺少技术人员对业务假设的   │
│        质疑和验证环节                                │
│  对策: 建立需求评审Checklist，强制包含边界场景确认    │
│  ═════════════════════════════════════════          │
│                                                     │
└─────────────────────────────────────────────────────┘
```

**注意事项**:
- 不要停留在表面原因（如"代码写错了"）
- 区分"人的错误"和"系统性问题"
- 每一层的Why都要有证据支撑
- 最终对策应能预防同类问题再次发生

### 3.2 鱼骨图分析法 (石川图/Ishikawa Diagram)

**原理**: 从多个维度系统地排查可能的原因。

```
                          缺陷现象
                            │
         ┌──────────────────┼──────────────────┐
         │                  │                  │
    ┌────┴────┐       ┌────┴────┐       ┌────┴────┐
    │  方法    │       │   人力   │       │   环境   │
    │ Method   │       │   Man    │       │Environment
    ├─────────┤       ├─────────┤       ├─────────┤
    •流程不规范 •技能不足  •测试环境差异
    •标准缺失   •培训不够  •数据配置不同
    •工具不当   •疲劳/疏忽  •网络/硬件
    •SOP不清   •沟通误解  •依赖服务波动
    └────┬────┘       └────┬────┘       └────┬────┘
         │                  │                  │
         └──────────────────┼──────────────────┘
                            │
         ┌──────────────────┼──────────────────┐
         │                  │                  │
    ┌────┴────┐       ┌────┴────┐       ┌────┴────┐
    │  测量    │       │   材料   │       │  机器   │
    │ Measure  │       │ Material │       │ Machine │
    ├─────────┤       ├─────────┤       ├─────────┤
    •度量不准  •需求模糊  •编译器/解释器
    •监控缺失  •接口变更  •IDE/编辑器
    •日志不全  •第三方库   •操作系统
    •指标误导  •数据质量  •部署容器
    └─────────┘       └─────────┘       └─────────┘
```

**AI时代的鱼骨图增强维度**:

```
    ┌──────────────┐
    │   🤖 AI因素   │  ← 新增维度!
    ├──────────────┤
    •Prompt设计不当
    •上下文窗口受限
    •模型幻觉/过拟合
    •训练数据偏差
    •AI工具版本变化
    •生成代码未review
    •过度信任AI输出
    └──────────────┘
```

### 3.3 缺陷模式匹配法

**原理**: 将当前缺陷与已知缺陷模式库进行比对，快速归类并复用已有解决方案。

详见第四章「缺陷模式库」。

### 3.4 故障树分析 (FTA - Fault Tree Analysis)

**原理**: 从顶层故障事件出发，自顶向下演绎分析所有可能的故障原因及其逻辑关系。

```
                      [订单创建失败]
                           │
              ┌────────────┼────────────┐
              │            │            │
         [参数校验失败] [库存不足]  [支付超时]
              │            │            │
       ┌──────┼──────┐     │       ┌────┴────┐
    [必填为空] [格式错误] [范围越] [SKU无效] [网关异常] [余额不足]
```

**适用场景**: 影响面大的P0/P1级故障的系统性分析。

## 四、缺陷模式库 (Defect Pattern Library)

### 4.1 AI生成代码典型缺陷模式

```
┌─────────────────────────────────────────────────────────────┐
│           AI生成代码 - 高频缺陷模式 TOP 10                    │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  🏆 Pattern #1: 边界/异常处理缺失 (出现率: 35%)             │
│  ├── 特征: 生成的代码只处理了happy path                     │
│  ├── 典型表现:                                             │
│  │   • 函数无返回值类型声明时的隐式undefined传播            │
│  │   • 数组操作无越界检查                                   │
│  │   • API调用无超时和重试设置                               │
│  │   • 数据库操作无事务保护                                 │
│  ├── 根因: AI倾向于生成"看起来正确"的最简代码                │
│  └── 防御: 强制要求AI同时生成异常处理路径的代码              │
│                                                             │
│  🥈 Pattern #2: 上下文幻觉 (出现率: 25%)                    │
│  ├── 特征: AI编造不存在的API、方法或参数                     │
│  ├── 典型表现:                                             │
│  │   • 调用了不存在的库函数                                 │
│  │   • 使用了错误的方法签名                                 │
│  │   • 引用了不存在的配置项                                 │
│  │   • 假设了不存在的全局变量                               │
│  ├── 根因: 概率生成机制导致"合理但不存在"的内容              │
│  └── 防御: 代码必须经过编译/类型检查 + 单元测试验证          │
│                                                             │
│  🥉 Pattern #3: 安全漏洞 (出现率: 15%)                      │
│  ├── 特征: AI生成的代码往往忽视安全最佳实践                 │
│  ├── 典型表现:                                             │
│  │   • SQL拼接而非参数化查询                                │
│  │   • 直接渲染用户输入(无转义)                              │
│  │   • 硬编码密钥/Token                                    │
│  │   • 缺少CSRF/XSS防护                                    │
│  │   • 权限校验不完整                                      │
│  ├── 根因: 训练数据中不安全代码占比高;安全非默认行为        │
│  └── 防御: 集成SAST/DAST安全扫描作为强制卡点               │
│                                                             │
│  Pattern #4: 性能隐患 (12%)                                │
│  ├── N+1查询、大数据集全量加载、无缓存策略、算法选择不当    │
│                                                             │
│  Pattern #5: 逻辑细微错误 (8%)                              │
│  ├── off-by-one、运算符优先级错误、短路求值陷阱             │
│                                                             │
│  Pattern #6: 一致性破坏 (3%)                                │
│  ├── 命名风格冲突、错误处理策略不一致、日志格式混乱         │
│                                                             │
│  Pattern #7: 测试质量伪高 (2%)                              │
│  ├── AI生成的测试只覆盖正向用例、mock过于宽松               │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 4.2 传统高频缺陷模式

```yaml
# 空指针/Null安全
Pattern-NPE-001:
  名称: "空引用解引用"
  频率: ★★★★★
  场景: 对象方法调用前未判空
  代码特征: "obj.method()" 且 obj 可能来自外部输入
  检测: 静态分析(Nullable注解)+ 运行时空指针检测

Pattern-NPE-002:
  名称: "集合操作空指针"
  频率: ★★★★☆
  场景: 对null对象调用stream/forEach/map等方法
  代码特征: "list.stream()" / "list.forEach(...)" 无前置null检查

# 资源管理
Pattern-RM-001:
  名称: "资源泄漏"
  频率: ★★★★☆
  场景: Connection/Stream/File/Lock 未关闭
  代码特征: open()/getConnection() 无对应的 finally/close()

Pattern-RM-002:
  名称: "连接池耗尽"
  频率: ★★★☆☆
  场景: 高并发下连接未归还
  代码特征: 异常路径跳过了returnToPool()

# 并发安全
Pattern-CONC-001:
  名称: "非原子 check-then-act"
  频率: ★★★★☆
  场景: 先检查后操作之间存在竞态
  代码特征: "if (map.get(k) == null) { map.put(k, v); }" 无同步

Pattern-CONC-002:
  名称: "不可变对象被修改"
  频率: ★★★☆☆
  场景: 共享的可变对象被多线程同时修改
  代码特征: 参数对象在方法内被修改且该对象可能在别处被访问

# 数据完整
Pattern-DI-001:
  名称: "脏读/幻读"
  频率: ★★★☆☆
  场景: 事务隔离级别不当导致的数据不一致
  代码特征: 读操作在写事务未提交时执行

# 业务逻辑
Pattern-BL-001:
  名称: "精度丢失"
  频率: ★★★★☆
  场景: 金额计算使用浮点数
  代码特征: float/double 用于金融运算

Pattern-BL-002:
  名称: "时区处理错误"
  频率: ★★★★☆
  场景: 跨时区的日期比较/显示
  代码特征: new Date() / datetime.now() 无时区信息
```

## 五、缺陷分析标准工作流

### 5.1 完整分析流程

```
┌─────────────────────────────────────────────────────────────┐
│                  缺陷分析标准工作流 (SOP)                    │
└─────────────────────────────────────────────────────────────┘

阶段1: 信息采集 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━ (30分钟内)
│
├── 1.1 缺陷基本信息记录
│   ├── 缺陷ID、标题、发现时间、发现人
│   ├── 复现步骤(精确到每一步操作)
│   ├── 期望结果 vs 实际结果
│   ├── 环境信息(版本/环境/数据/账号)
│   └── 截图/日志/堆栈信息
│
├── 1.2 影响范围评估
│   ├── 影响用户数量/比例
│   ├── 影响功能模块
│   ├── 是否有规避方案
│   └── 业务损失估算(如有)
│
└── 输出: 《缺陷采集记录单》


阶段2: 分类定级 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━ (发现问题当时)
│
├── 2.1 类型分类 (参照ODC分类体系)
│   ├── 功能性 / 系统性 / 接口 / 数据 / 安全 / UI
│   └── 打上具体子标签 (如: F4-边界条件处理不当)
│
├── 2.2 来源分类 (AI时代增强版)
│   ├── 人为(H1-H5) / AI(AI1-AI7) / 流程(P1-P4) / 需求(R1-R4)
│   └── 这一步对后续改进方向至关重要!
│
├── 2.3 严重程度定级
│   ├── P0致命 / P1严重 / P2一般 / P3轻微 / P4建议
│   └── 结合影响范围和复现概率综合判定
│
└── 输出: 《缺陷分类标签》


阶段3: 根因分析 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━ (修复完成后48h内)
│
```

```python
# Pareto分析步骤
"""
1. 按缺陷类型统计数量
2. 按数量降序排列
3. 计算累计百分比
4. 找出贡献80%缺陷的前20%类型
5. 针对这少数重点类型制定改进措施

示例输出:
┌────────────────────┬───────┬──────────┐

│ 其他               │  18   │ 100%     │
└────────────────────┴───────┴──────────┘

结论: 重点解决前4类问题即可消除80%的缺陷
"""
```
