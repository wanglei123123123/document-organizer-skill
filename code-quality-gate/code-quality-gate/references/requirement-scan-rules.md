# 需求文档质量检测规则库 (Requirement Scan Rules)

> 本文件定义针对**文本需求文档**（PRD、用户故事、规格说明书等）的质量检测规则。
> 将测试方法论（边界值、等价类、因果图、错误推测）映射到**需求层面**的检测项，
> 在编码前发现需求缺陷，实现"需求左移"。

## 详细规则定义

### REQ-COMP 组 — 需求完整性（来自边界值分析 + 因果图 + 错误推测）

#### REQ-COMP-01: 核心业务流程缺失
```yaml
规则ID: REQ-COMP-01
名称: "核心业务主流程描述缺失或不完整"
方法来源: 因果图法
严重程度: BLOCKER
适用文档: PRD / 功能规格说明书 / 用户故事
检测逻辑:
  检查项:
  - 是否有明确的"正常流程"/"主流程"/"Happy Path"描述?
  - 主流程是否从起点到终点完整闭环?
  - 是否每个主要功能模块都有对应的流程说明?

  检测信号 (NLP关键词):
    ❌ 缺失信号:
      - 文档中无 "流程" "步骤" "flow" "process" 关键词
      - 只有功能列表但没有操作序列
      - 用户故事只有标题没有 Acceptance Criteria
    
    ✅ 合格信号:
      - 有 "主流程" "正常流程" "基本流程" 明确章节
      - 有流程图 (mermaid/流程图图片)
      - 用户故事有 Given-When-Then 格式的 AC

  典型反例:
    "系统支持用户注册和登录"
    # → 缺少: 注册流程的具体步骤是什么? 登录有几种方式?

  正确示例:
    """
    ## 用户注册流程 (主流程)
    1. 用户点击「注册」按钮
    2. 系统展示注册表单 (手机号/邮箱 + 密码 + 验证码)
    3. 用户填写信息并点击「获取验证码」
    4. 系统发送验证码到用户手机/邮箱
    5. 用户输入验证码并点击「提交」
    6. 系统校验信息合法性
    7. 创建用户账号,跳转到首页
    """

建议措施:
  补充完整的业务主流程描述,推荐使用:
  - 编号步骤列表 (1. 2. 3. ...)
  - 流程图 (mermaid/Visio)
  - 用户故事的 Given-When-Then 格式
```

#### REQ-COMP-02: 边界值场景未定义
```yaml
规则ID: REQ-COMP-02
名称: "数值/长度/数量等边界场景在需求中未明确定义"
方法来源: 边界值分析法
严重程度: CRITICAL
适用文档: ALL
检测逻辑:
  检查需求中涉及以下内容时,是否给出了边界约束:

  边界类型检查清单:
  ┌──────────────┬─────────────────────┬──────────────────────────┐
  │ 类型          │ 需关注边界           │ 需求中应有的描述          │
  ├──────────────┼─────────────────────┼──────────────────────────┤
  │ 数值范围      │ 最小/最大值          │ "支持 X ~ Y 的值"        │
  │ 字符串长度    │ 最短/最长           │ "限制 N ~ M 个字符"       │
  │ 列表/集合数量 │ 最少/最多条目数      │ "单次最多选择 N 项"       │
  │ 文件大小      │ 上限               │ "最大不超过 X MB"         │
  │ 时间范围      │ 起始/截止/时长      │ "支持查询近 N 天的数据"    │
  │ 分页          │ 每页条数/总页数上限  │ "每页 N 条,最多 N 页"     │
  │ 并发数        │ 最大同时操作数       │ "最多支持 N 人同时编辑"    │
  │ 层级深度      │ 最大嵌套层数         │ "评论最多回复 N 层"       │
  │ 金额/价格     │ 最小/最大/精度       │ "支持 0.01 ~ 99999.99"   │
  │ 年龄/日期     │ 有效范围            │ "适用于 18~60 岁用户"      │
  └──────────────┴─────────────────────┴──────────────────────────┘

  检测信号:
    ❌ 问题信号:
      - 出现 "若干" "多个" "适当" "合理" 等模糊量词
      - 有数值字段但无范围限制说明
      - 有上传/导入功能但无大小限制
      - 有分页但无每页条数/总数上限
    
    ✅ 合规信号:
      - 每个数值参数都有 [min, max] 定义
      - 使用表格列出所有限制条件
      - 有专门的"数据约束"或"限制条件"章节

  典型反例:
    "用户可以上传头像"
    # → 边界缺失: 大小? 格式? 尺寸? 

  正确示例:
    """
    ### 头像上传约束
    | 属性    | 约束                              |
    |--------|-----------------------------------|
    | 文件大小 | ≤ 2MB                            |
    | 格式    | JPG, PNG, WebP                    |
    | 尺寸    | 建议 ≥ 200×200px, 自动压缩至 256×256 |
    | 比例    | 1:1 (正方形)                      |
    """

建议措施:
  为每个涉及数值/长度的需求项建立约束表,
  至少包含: 最小值、最大值、默认值、单位
```

```yaml
规则ID: REQ-COMP-03
名称: "异常流程、错误场景、失败处理在需求中未描述"
方法来源: 错误推测法
严重程度: CRITICAL
适用文档: ALL
检测逻辑:
  基于错误推测法的典型异常场景检查清单:

  必须描述的异常场景:
  ┌────────────────────────────────────────┐
  │  💡 错误推测法 — 需求异常场景 Checklist │
  ├────────────────────────────────────────┤
  │  输入相关异常:                          │
  │  ☐ 输入为空/未填写怎么办?                │

  │  ☐ 输入超长/超大怎么办?                 │
  │  ☐ 输入含特殊字符/脚本怎么办?            │
  │  ☐ 输入包含敏感词怎么办?                │
  │                                        │
  │  系统相关异常:                          │
  │  ☐ 网络超时/断网怎么办?                 │
  │  ☐ 服务端报错(500)怎么办?              │
  │  ☐ 并发冲突(重复提交)怎么办?           │
  │  ☐ 权限不足怎么办?                      │
  │  ☐ 资源不存在(404)怎么办?              │
  │                                        │
  │  业务相关异常:                          │
  │  ☐ 库存不足怎么办?                      │
  │  ☐ 余额不足怎么办?                      │
  │  ☐ 已存在/重复操作怎么办?              │
  │  ☐ 状态不允许的操作怎么办?             │
  │  ☐ 达到频率/次数限制怎么办?            │
  │                                        │
  │  数据相关异常:                          │
  │  ☐ 数据校验失败怎么办?                 │
  │  ☐ 数据关联丢失怎么办?                 │
  │  ☐ 数据格式不兼容怎么办?               │
  └────────────────────────────────────────┘

  检测信号:
    ❌ 问题信号:
      - 只有正常流程,无任何异常流程描述
      - "出错时提示错误信息" 但未说明具体每种错误的处理
      - 无 "异常流程" "错误处理" "边界情况" 章节
      - User Story 只有 happy path 的 AC
    
    ✅ 合规信号:
      - 有 "异常流程" "错误场景" "边界情况" 专门章节
      - 每个主要功能至少有 1-2 个异常场景
      - 使用 "扩展流程" (Extend) 或 "替代流程" (Alternative) 描述

建议措施:
  为每个核心功能至少补充 3 类异常场景:
  1. 输入异常 (空值/格式错/越界)
  2. 系统异常 (超时/服务不可用)
  3. 业务异常 (状态冲突/权限不够)
```

#### REQ-COMP-04: 前置/后置条件不明确
```yaml
规则ID: REQ-COMP-04
名称: "操作的前置条件和后置效果未明确声明"
方法来源: 等价类划分法
严重程度: MAJOR
适用文档: User Story / 用例规格 / API文档
检测逻辑:
  每个功能操作应该明确:
  
  Pre-condition (前置条件):
  - 操作前必须满足什么状态?
  - 用户需要具备什么权限/角色?
  - 需要哪些前置数据已就绪?
  - 是否依赖其他功能先完成?
  
  Post-condition (后置效果):
  - 操作成功后系统状态如何变化?
  - 会产生什么通知/日志/事件?
  - 相关数据如何更新?
  - 用户能看到什么反馈?

  检测信号:
    ❌ 问题:
      - "管理员可以删除用户" — 但未说明:
        - 删除的用户正在在线怎么办?(前置)
        - 删除后该用户的订单/数据怎么处理?(后置)

建议措施:
  采用标准格式:
  """
  ## 功能: 删除用户
  
  **Pre-conditions (前置条件):**
  - 当前登录用户拥有「用户管理」权限
  - 目标用户处于「正常」或「禁用」状态 (不可删除已注销用户)
  - 目标用户当前不处于在线状态
  
  **Post-conditions (后置效果):**
  - 成功: 用户状态变更为「已注销」,保留历史数据
  - 系统发送通知给被删除用户 (如有绑定联系方式)
  - 操作记录写入审计日志
  - 该用户的所有活跃 Session 强制下线
  """
```

#### REQ-COMP-05: 非功能需求(NFR)缺失
```yaml
规则ID: REQ-COMP-05
名称: "性能/安全/可用性等非功能需求未定义或过于简略"
方法来源: 错误推测法
严重程度: MAJOR
适用文档: PRD / 规格说明书
检测逻辑:
  NFR检查矩阵:
  ┌──────────┬──────────────────────────────────────────┐
  │ NFR类别   │ 应有的描述                                │
  ├──────────┼──────────────────────────────────────────┤
  │ 性能     │ 响应时间(P50/P95/P99)/并发量/吞吐量       │
  │ 安全     │ 认证方式/加密/审计/数据保留/合规           │
  │ 可用性   │ SLA目标/降级策略/容灾/备份                │
  │ 可维护性 │ 日志规范/监控指标/配置外部化              │
  │ 兼容性   │ 浏览器版本/OS/屏幕分辨率/API版本          │
  │ 可扩展性 │ 预期用户规模/数据增长规划/水平扩展方案    │
  │ 国际化   │ 多语言/多时区/多币种/本地化格式          │
  └──────────┴──────────────────────────────────────────┘

  检测信号:
    ❌ 问题:
      - 整份文档无任何 NFR 章节
      - 性能只写了 "要求快速" "响应及时"
      - 安全只写了 "保证安全"

建议措施:
  建立 NFR 专门章节,使用量化指标:
  """
  ## 非功能需求
  
  ### 性能指标
  | 场景          | P50   | P95   | P99   |
  |--------------|-------|-------|-------|
  | 首页加载      | <1s   | <2s   | <3s   |
  | 搜索结果      | <500ms| <1s   | <2s   |
  | API接口响应   | <200ms| <500ms| <1s   |
  
  ### 安全要求
  - 密码: BCrypt加密,最少8位含大小写+数字+特殊字符
  - 传输: 全站 HTTPS (TLS 1.2+)
  - 认证: JWT Token, 过期时间 24h, Refresh Token 7天
  - 审计: 所有写操作记录操作人+时间+IP+内容摘要
  """
```

### REQ-CLAR 组 — 需求清晰度（来自等价类划分 + 因果图）

#### REQ-CLAR-01: Acceptance Criteria 模糊或缺失
```yaml
规则ID: REQ-CLAR-01
名称: "User Story的验收标准模糊、缺失或不可验证"
方法来源: 边界值分析法
严重程度: BLOCKER
适用文档: User Story / Ticket
检测逻辑:
  AC质量标准:
  
  ✅ 好的AC (INVEST原则):
  - Independent (独立的): 不与其他AC强耦合
  - Negotiable (可协商的): 细节可讨论
  - Valuable (有价值的): 对用户/业务有意义
  - Estimable (可估算的): 开发能估算工作量
  - Small (小的): 单个迭代可完成
  - Testable (可测试的): 能明确判断通过/失败

  ❌ 差的AC:
  - "系统运行良好" → 什么叫良好? 不可验证!
  - "提高用户体验" → 怎么衡量? 太主观!
  - "界面美观大方" → 美观的标准是什么?
  - "支持各种设备" → 各种 = ? 需要列举!

  检测信号:
    - AC 中出现: 很好、较快、方便、合理、优化、改善 等形容词
    - 没有 AC (User Story 只有 Title 和 Description)

建议措施:
  重写为可验证的格式:
  ❌ "搜索速度要快"
  ✅ "在 100万条数据条件下,搜索响应时间 P95 < 500ms"
  
  推荐 Gherkin Given-When-Then 格式:
  """
  Scenario: 用户成功搜索商品
    Given 用户在搜索页输入 "iPhone"
    And 商品库中有 50 个包含 "iPhone" 的商品
    When 用户点击搜索按钮
    Then 系统在 500ms 内返回搜索结果
    And 结果按相关性排序展示前20条
    And 每条结果包含: 图片、名称、价格、评分
  """
```

#### REQ-CLAR-02: 存在歧义或多义词
```yaml
规则ID: REQ-CLAR-02
名称: "需求文档中使用可能产生多种理解的词汇"
方法来源: 等价类划分法
严重程度: CRITICAL
适用文档: ALL
检测逻辑:
  高频歧义词汇表:
  ┌──────────────┬──────────────────────────────────────┐
  │ 歧义词       │ 可能的理解 (至少2种)                 │
  ├──────────────┼──────────────────────────────────────┤
  │ "可以"       │ 允许做 vs 系统能够做                │
  │ "应该"       │ 建议做 vs 必须做                     │
  │ "用户"       │ 普通用户 vs 管理员 vs 游客          │
  │ "支持"       │ 必须支持 vs 可以支持                │
  │ "适时"       │ 什么时候? 无明确时间点               │
  │ "适当"       │ 什么程度合适? 无标准                │
  │ "等等"       │ 还有什么? 范围不明                   │
  │ "类似"       │ 具体是什么? 要举例                   │
  │ "常规"       │ 常规的定义是什么?                   │
  │ "尽量"       │ 不是必须? 那做不到怎么办?            │
  │ "可能"       │ 一定会发生还是可能发生?              │
  │ "偶尔"       │ 频率是多少? 1%? 10%?                │
  │ "简单"       │ 对谁来说简单?                       │
  │ "快速"       │ 多快算快? 需要量化                   │
  └──────────────┴──────────────────────────────────────┘

  检测信号:
    - 文档中出现上述词汇且无附加解释
    - 不同人对同一段需求的解读不一致

建议措施:
  1. 建立项目术语表 (Glossary),统一所有专业词汇定义
  2. 用具体的数值/枚举值替换模糊词:
     "快速" → "P95响应时间 < 1秒"
     "可以" → "必须支持" 或 "可选支持"
  3. 对每个可能有歧义的词汇添加脚注注释
```

#### REQ-CLAR-03: 需求之间互相矛盾
```yaml
规则ID: REQ-CLAR-03
名称: "不同章节/不同需求之间的描述存在直接或间接矛盾"
方法来源: 因果图法
严重程度: BLOCKER
适用文档: PRD / 规格说明书
检测逻辑:
  常见矛盾类型:
  
  1. 数值矛盾:
     - A章说 "密码最短6位", B章说 "密码至少8位"
     - A章说 "单次最多选10项", B章说 "批量操作上限50"
  
  2. 流程矛盾:
     - A流程说 "先审批再执行", B流程说 "先执行后补审批"
     - A处说 "需要二次确认", B处同类操作却说 "无需确认"
  
  3. 状态矛盾:
     - A处说 "订单取消后不可恢复", B处说 "支持恢复已取消订单"
  
  4. 权限矛盾:
     - A处说 "普通用户可编辑", B处说 "仅管理员可编辑"
  
  5. 时间矛盾:
     - A处说 "T日数据次日可查", B处说 "实时查询(T+0)"

  检测方法:
  - 提取所有带数值/布尔/枚举的约束声明
  - 对比同一主题的不同描述是否一致
  - 构建状态机/流程图,检查是否存在冲突路径

建议措施:
  1. 建立单一数据源: 所有可能变化的值集中在一个地方定义
  2. 使用交叉引用: "详见第X章 Y节"
  3. 需求评审时专门进行"矛盾排查"环节
```

#### REQ-CLAR-04: 依赖关系未声明
```yaml
规则ID: REQ-CLAR-04
名称: "需求之间的依赖关系(内部依赖/外部依赖)未明确声明"
方法来源: 因果图法
严重程度: CRITICAL
适用文档: 迭代计划 / 发布计划 / PRD
检测逻辑:
  依赖类型检查:
  ┌──────────────────────────────────────────┐
  │ 内部依赖 (项目内功能间依赖)               │
  ├── 功能B依赖功能A先完成                    │

  ├── 接口依赖: B功能需要A提供的API           │
  └── 配置依赖: B功能的开关受A功能影响         │

  │ 外部依赖 (项目外依赖)                     │

  检测信号:
    - 需求提到了 "对接XX系统" 但没说对方何时就绪

    - 迭代计划中的需求顺序未考虑依赖关系

建议措施:
  建立依赖关系矩阵/图:
  """
```

#### REQ-TEST-01: 无法验证的需求（主观描述）
```yaml
规则ID: REQ-TEST-01
名称: "需求描述过于主观,无法设计测试用例来验证是否满足"
方法来源: 错误推测法
严重程度: CRITICAL
适用文档: ALL
检测逻辑:
  无法验证的模式:
  
  ❌ 主观词汇黑名单:
    "用户体验好" "界面美观" "操作流畅" "系统稳定" 
    "易于使用" "符合直觉" "专业感强" "高端大气"
    
  → 这些描述无法转换为 PASS/FAIL 的测试断言
  
  ✅ 可验证的重写:
    "用户体验好" → "新手用户完成核心任务的平均操作步骤 ≤ 5步"
    "界面美观" → "UI设计稿经设计评审通过,符合设计规范 v2.0"
    "操作流畅" → "页面切换动画帧率 ≥ 60FPS; 操作响应延迟 < 100ms"
    "系统稳定" => "连续运行7天无宕机; 内存泄漏增长率 < 1MB/h"
```

### REQ-SEC 组 — 安全与权限（来自等价类 + 错误推测）

#### REQ-SEC-01: 权限角色定义不完整
```yaml
规则ID: REQ-SEC-01
名称: "系统的用户角色/权限矩阵定义不完整或有遗漏"
方法来源: 等价类划分法
严重程度: BLOCKER
适用文档: PRD / 权限设计文档
检测逻辑:
  权限矩阵检查:
  - 是否列出了所有角色 (超级管理员/管理员/普通用户/访客/...)?
  - 每个功能点的权限是否都有定义 (可见/可操作/不可见)?
  - 是否有"最小权限原则"的考虑?
  - 数据权限 (行级/字段级) 是否定义?
  
  等价类视角:
  - 角色的等价类: 每种角色是一个等价类
  - 对每个功能,检查所有角色的权限是否都已分配
  - 特别注意: 新增角色时是否遗漏了某功能的权限配置
```

#### REQ-SEC-02: 敏感数据处理规则缺失
```yaml
规则ID: REQ-SEC-02
名称: "个人隐私信息/敏感商业数据的收集/存储/使用/销毁规则未定义"
方法来源: 错误推测法
严重程度: CRITICAL
适用文档: PRD / 隐私政策 / 合规文档
检测逻辑:
  敏感数据生命周期检查:
  - 收集: 采集了哪些敏感数据? 为什么需要? 是否最小必要?
  - 存储: 加密方式? 存储位置? 访问控制?
  - 使用: 哪些场景可以使用? 是否脱敏?
  - 传输: 传输加密? 接口鉴权?
  - 展示: 日志/报表中是否脱敏? 导出时是否加密?
  - 销毁: 保留期限? 销毁方式? 用户是否有权要求删除(GDPR)?
```

## 需求质量评分模型

### 综合评分公式

```
需求质量总分 = w1×完整性 + w2×清晰度 + w3×可测试性 + w4×安全性

其中:
  完整性 (COMP)  = 通过的COMP规则数 / 总COMP规则数 × 100
  清晰度 (CLAR)  = 通过的CLAR规则数 / 总CLAR规则数 × 100
  可测试性(TEST) = 通过的TEST规则数 / 总TEST规则数 × 100
  安全性 (SEC)   = 通过的SEC规则数 / 总SEC规则数 × 100

权重: w1=0.3, w2=0.25, w3=0.25, w4=0.2
```

### 评级标准

| 等级 | 分数范围 | 门禁结果 | 含义 |
|------|----------|----------|------|
| A 优秀 | 90-100 | ✅ PASS | 需求质量高,可直接进入设计/开发 |
| B 良好 | 75-89 | ⚠️ WARN | 有少量问题,建议修补后进入下一阶段 |
| C 合格 | 60-74 | ⚠️ WARN | 存在较多问题,强烈建议修订 |
| D 不合格 | <60 | 🔴 BLOCK | 需求质量问题严重,禁止进入开发 |

### 快速自检Checklist

```
需求文档质量自检表 (Top 10 关键检查项)
══════════════════════════════════════════

□ 1. 每个功能都有完整的主流程描述吗?           (COMP-01)
□ 2. 所有数值参数都定义了[min, max]范围吗?       (COMP-02)
□ 3. 至少描述了3个异常/错误场景吗?             (COMP-03)
□ 4. Acceptance Criteria 都是可验证的吗?        (CLAR-01)
□ 5. 没有使用"快速""方便""合理"等模糊词吗?     (CLAR-02)
□ 6. 不同段落之间没有矛盾吗?                   (CLAR-03)
□ 7. 外部和内部依赖都声明了吗?                 (CLAR-04)
□ 8. 角色-功能权限矩阵完整吗?                  (SEC-01)
□ 9. 敏感数据的处理规则定义了吗?               (SEC-02)
□ 10. 非功能需求有量化指标吗?                  (COMP-05)

通过数: ___ / 10    预估质量等级: ___
```
