# 测试用例设计规范与Markdown输出模板

> 本文件定义测试用例的**设计规范**、**编写规范**和**标准Markdown输出格式**。
> 当使用 code-quality-gate Skill 生成测试用例时，必须同时遵循本文件中的规范和格式。

---

## 一、用例设计规范

### 1.1 概述

测试用例是自动化测试用例编写、测试执行的基础。设计好的用例，才能保证测试的覆盖度。

测试用例作为执行文档，必须遵循两个基本原则：
1. **可以被他人理解** — 任何人阅读测试用例都能读懂，没有歧义
2. **可以被他人执行** — 任何人拿到用例都能按描述找到对应入口并执行

### 1.2 用例五大基本元素

| 元素 | 英文 | 说明 |
|------|------|------|
| **功能/模块** | Feature | 被测功能点所属功能/模块（最小的功能子节点） |
| **测试场景** | Scenario | 具体的测试功能点，或针对功能点的用户使用场景 |
| **前提条件** | Given | 需要达到什么条件才能使用例可执行 |
| **操作步骤** | When | 如何操作才能达到预期结果 |
| **预期结果** | Then | 按照前提条件和操作步骤操作最终呈现的结果 |

### 1.3 用例设计两个阶段

| 阶段 | 包含内容 | 编写人员素质要求 |
|------|----------|------------------|
| **用例设计阶段** | 用例目录、测试场景 | 1. 扎实的业务基础 2. 掌握被测需求 3. 丰富的用例设计经验 4. 较强质量把控意识 5. 了解代码实现逻辑 |
| **用例编写阶段** | 前提条件、操作步骤、预期结果 | 1. 熟悉被测需求 2. 掌握用例编写基础知识 3. 熟练运用用例设计方法 |

## 二、用例设计阶段原则与规范

### 2.1 原则：独立 + 完整

- **独立**: 被测模块独立，是一个独立的、可测试的功能模块
- **完整**: 测试场景要完整，从用户使用场景出发，进行边界值、等价类等全场景的覆盖

### 2.2 目录结构规范

```
目录结构 = 模块(Dir) → 功能(Dir) → 子功能(Feature)

规则:
├── 模块(一级目录): 按产品形态划分，要符合代码结构，与研发侧确认
├── 功能(二级目录): 模块下的功能点，按代码结构划分
└── 子功能(最小节点): 功能下更细节的功能细分
    ├── 同一层级按同一维度划分
    ├── 子功能是最小功能点的子节点
    ├── 被测功能较大时 → 拆分到子功能
    └── 被测功能较小时 → 直接放在模块下面
```

**示例:**
```
基本格式/                    ← 模块(一级)
├── 标题/                    ← 功能(二级)
├── 段落/                    ← 功能(二级)
├── 图片/                    ← 功能(二级)
│   ├── 插入图片              ← 子功能(三级)
│   ├── 裁剪图片              ← 子功能(三级)
│   └── 操作图片              ← 子功能(三级)
├── 批注/                    ← 功能(二级)
└── 水印                     ← 功能较小，直接在模块下
```

### 2.3 测试场景(Scenario)命名规范

测试场景 = 用例标题，是用户的实际使用场景。

**规范要求:**
1. 场景命名要**描述清晰**: 用户使用场景或测试目的
2. 命名**简单易懂**, 不包含操作步骤
3. 从用户实际使用场景出发(入口、不同位置、不同格式等)

**示例:**
```
✅ Good:
  - "通过拖拽方式插入本地图片到文档正文"
  - "搜索结果为空时展示空状态引导"
  - "QQ账号登录后切换微信账号"

❌ Bad:
  - "点击插入按钮选择图片" → 这是操作步骤，不是场景
  - "测试图片" → 太模糊，不知道测什么
  - "图片bug验证" → 不是用户场景
```

## 三、用例编写阶段原则与规范

### 3.1 四大编写原则

#### 原则一: DRY — Don't Repeat Yourself（正交 + 原子）

**正交**: 不同的用例不会重复验证同一个测试点
> 为了保证覆盖完整，适度的重复可以接受

```
❌ Bad (重复验证):
  用例1: 验证"生成长图-清晰度"权限(会员/非会员)
  用例2: 验证"生成长图-水印设置"权限(会员/非会员)
  用例3: 从功能角度再次验证清晰度权限 ← 重复!
  用例4: 从功能角度再次验证水印权限   ← 重复!

✅ Good:
  用例1: 验证"生成长图-清晰度"权限(会员/非会员)
  用例2: 验证"生成长图-水印设置"权限(会员/非会员)
  (不再从另一个角度重复验证同一功能)
```

**原子**: 每个测试用例只验证一个测试点，多于一个点需拆分

```
❌ Bad (多个验证点):
  Scenario: 生成副本后编辑
    Given 打开一个非空文档
      When 点击生成副本
        Then 显示新副本，内容格式与原文档一致，且可以编辑输入文字
  → 同时验证了"生成副本"和"编辑副本"两个点!

✅ Good (拆分为独立用例):
  Scenario: 生成副本
    Given 打开一个非空文档
      When 点击文档操作生成副本
        Then 显示新生成的副本，内容格式与原文档一致

  Scenario: 编辑副本文档
    Given 文档列表中有刚生成的副本文档
      When 打开副本文档，在正文点击鼠标，在光标定位处输入文字
        Then 输入文字成功
```

#### 原则二: DAMP — Descriptive and Meaningful Phrases（可读性）

- 描述精炼，避免大段重复
- 语言准确，没有歧义，尽量具体化
- 功能入口或操作，采用**通用的专业名称**

```
❌ Bad (不专业，不清晰):
  Scenario: 正切侧
    When 已有批注内容，正文展示模式下，点击批注，切换到侧边展示模式
      Then 1、正文里不再显示批注块 2、侧边栏出现批注内容...
  → "正切侧"不是专业名称; 断言描述不清晰

✅ Good (专业名称，清晰断言):
  Scenario: 批注显示模式从嵌入正文切换到侧边栏
    Given 文档中已有3条批注，当前为嵌入正文模式
      When 点击批注面板右上角"切换到侧边栏模式"按钮
        Then 正文中不再显示批注色块
        Then 右侧出现批注侧边栏，3条批注按从上到下顺序展示
        Then 每条批注包含: 批注人头像、昵称、时间、批注内容
        Then 批注位置与正文对应内容水平对齐
```

#### 原则三: 可判定 + 可回归

- 预期明确可判定，多次执行结果保持一致
- 同样的条件，不同的人，不同的时间执行结果一致

```
❌ Bad (不可判定):
  Scenario: 文字拖拽
    Given PC端可编辑文档
      When 选中正文中的任意内容；长按选区进行拖拽
        Then 选区的内容被插入到指定的位置，格式保留
  → "任意内容"不明确! "指定的位置"不明确! 不同人执行结果不同

✅ Good (明确可判定):
  Scenario: 拖拽普通文本到段落末尾
    Given PC端打开可编辑文档，正文包含"测试文本"和目标段落
      When 选中"测试文本"4个字，长按拖拽到目标段落末尾释放
        Then "测试文本"从原位置消失
        Then "测试文本"出现在目标段落末尾，字体格式与原格式一致
```

#### 原则四: 独立

- 用例之间彼此独立，不存在互相依赖
- 用例A的执行不能依赖于用例B的执行结果

> **DRY 与 DAMP 的平衡**: DRY要求简练不重复，DAMP要求描述清晰具体化。两者存在冲突时，根据用例场景取舍判断。

### 3.2 各元素编写规范

#### 前提条件 (Given) 规范

| # | 规则 | 说明 |
|---|------|------|
| G-1 | ❌ 不能将其他用例作为前置条件 | 如"执行用例TC-003后" 是错误的 |
| G-2 | ✅ 执行条件正确，符合使用场景 | 条件要真实可达 |
| G-3 | ✅ 描述清晰完整 | 包括但不限于: 入口、账号、权限、输入数据等 |
| G-4 | ❌ **不能出现"或""分别"等选择性/多选项词语** ⚠️ | 前提条件涉及多个选项时**必须拆分为多条用例** |
| G-5 | ⚠️ **例外: 兼容性测试整合为1条用例** | 系统版本/安装版本/引擎等兼容性维度用表格列举，不逐一拆分 |

> **G-4 重点说明**: 前提条件中出现"或""分别""/""/""任意""不同"等词语时，
> 说明一条用例试图覆盖多种前提场景，必须拆为每种前提各一条用例。
> 每条用例的前提条件必须是唯一确定的环境/状态。

> **G-5 例外说明**: 当"不同的前提"属于**兼容性测试范畴**（系统版本、安装版本、
> 引擎类型、显卡型号、分辨率、DPI等硬件/环境组合）时，**整合为1条兼容性用例**，
> 用表格列出需验证的环境组合，不逐一拆分。
> 原因: 兼容性用例的操作步骤和预期结果相同，仅环境不同，逐一拆分会产生大量冗余用例。

```
G-4 适用（需拆分）vs G-5 例外（整合为1条）的判断标准:

  需拆分的情况 (G-4):
  ├── 不同前提导致操作步骤不同  → 拆分
  ├── 不同前提导致预期结果不同  → 拆分
  └── 不同前提涉及不同的业务逻辑 → 拆分
      例: QQ登录 vs 微信登录 → 授权流程不同 → 拆分
      例: Wi-Fi vs 弱网 → 预期结果不同(秒开 vs 加载中) → 拆分
      例: 已登录 vs 未登录 → 操作路径不同(直接下载 vs 先登录) → 拆分

  整合为1条的情况 (G-5):
  ├── 不同前提的操作步骤完全相同  → 整合
  ├── 不同前提的预期结果完全相同  → 整合
  └── 差异仅在于运行环境/硬件配置 → 整合
      例: Win10 vs Win11 → 同样的操作，同样的预期 → 整合
      例: VBox vs Hyper-V vs NEMU → 同功能验证 → 整合
      例: OpenGL vs Vulkan vs DX11 → 同功能验证 → 整合
      例: v3.0→v3.2升级 vs v2.8→v3.2升级 → 同操作同预期 → 整合
```

```
❌ Bad (兼容性逐一拆分，大量冗余):
  TC-COMPAT-001: Win10环境下启动应用宝
    Given Windows 10 22H2系统
    When 双击应用宝图标
    Then 应用宝正常启动

  TC-COMPAT-002: Win11环境下启动应用宝
    Given Windows 11 23H2系统
    When 双击应用宝图标
    Then 应用宝正常启动

  TC-COMPAT-003: Win10 LTSC环境下启动应用宝
    ...
  → 问题: 操作和预期完全相同，拆成N条全是冗余!

✅ Good (兼容性整合为1条，用表格列举环境):
  TC-COMPAT-001: 不同操作系统版本下启动应用宝

  - **优先级**: P1
  - **所属模块**: 启动 > 兼容性
  - **测试方法**: 正交实验法 - 兼容性测试

#### 操作步骤 (When) 规范

| # | 规则 | 说明 |
|---|------|------|
| W-1 | ✅ 符合语法结构: 主谓宾/动宾结构 | "点击搜索按钮" "输入关键词" |
| W-2 | ❌ 不能出现连词/介词 | "而且""和""或" 需拆成多步 |
| W-3 | ❌ **不能出现"或"等选择性/多选项词语** ⚠️ | 涉及不同场景或不同操作路径时**必须拆分为多条用例** |
| W-4 | ❌ 不能出现假设性词汇 | "如果""假设""可能" |
| W-5 | ❌ 不建议出现操作后的预期 | "弹出XX""出现XX" 应放在Then |
| W-6 | ✅ 有明确的操作动作和输入信息 | 点击什么、输入什么、选择什么 |
| W-7 | ✅ A功能必须经过B功能时，B功能放入Given | 减少步骤冗余 |
| W-8 | ✅ **多场景/多页面时拆分用例，标题用场景名/页面名区分** ⚠️ | 一条用例只在一个场景/一个页面内操作 |

> **W-3 重点说明**: 操作步骤中出现"或""/""/""也可以""任选其一"等词语时，
> 说明一条用例中混入了多个操作路径，必须拆分为独立用例。
> 每条用例的操作路径必须是唯一确定的，不同人执行时走同一条路径。

> **W-8 重点说明**: 当操作步骤涉及多个场景或多个页面时，必须按场景/页面拆分为多条用例。
> 用例标题必须包含**场景名称或页面名称**作为区分标识，使用例归属清晰明确。
> 命名格式: `{功能描述}-{场景名/页面名}`

```
❌ Bad (多个页面混在一条用例中):
  Scenario: 下载状态显示正确
    When 点击下载"王者荣耀"
      Then 首页、我的页面、下载盒子页面均显示下载进度
  → 问题: 3个页面的验证混在一条用例中! 各页面表现可能不同

❌ Bad (多个场景混在一条用例中):
  Scenario: 更新应用
    When 在更新列表页/我的页面/快捷工具栏 点击更新按钮
      Then 应用开始更新
  → 问题: 3个入口场景混在一起! 每个入口是独立的操作路径

✅ Good (按页面拆分，标题含页面名):
  TC-DL-010: 下载进度显示-首页
    Given 使用QQ账号登录应用宝
    When 在首页点击"王者荣耀"下载按钮
    Then 首页该应用卡片显示下载进度条，进度百分比实时更新

  TC-DL-011: 下载进度显示-我的页面
    Given 使用QQ账号登录，已触发"王者荣耀"下载
    When 切换到"我的"页面
    Then "我的"页面应用列表中"王者荣耀"显示下载进度条

## 四、优先级标签规范

> 优先级标签是用例的核心属性，决定了测试执行的顺序和覆盖策略。
> 必须严格按照以下标准定义每条用例的优先级。

### 4.1 优先级定义

| 优先级 | 占比(建议) | 适用场景 | 详细定义 |
|--------|-----------|----------|----------|
| **P0** | **15%** | 开发自测 / 回归测试 / 集成测试 / 上线前测试 / 耦合功能变更被波及 / 集成用例新合入功能验证 | 见下文 |
| **P1** | **65%** | 增量测试 | 见下文 |
| **P2** | **20%** | 增量测试 | 见下文 |

#### P0 — 核心必测（约15%）

```
P0 用例入选标准（满足任一即可标为P0）:

  1. 需求中明确说明的功能点，入口及对应的操作路径
  
  2. 功能的核心模块的主流程
     → 如果执行不通过会影响其他功能验证
     → 或者其他路径的执行依赖此用例
  
  3. 核心功能交叉场景:
     ├── 下载状态一致性检查
     ├── 下载能力的检查
     └── 不同登录状态的检查（QQ/微信/未登录）
  
  4. 页面UI显示不错乱（核心页面的基本渲染正确性）
```

**P0 使用场景:**
- 开发自测（研发提测前必须通过全部P0）
- 回归测试 / 集成测试 / 上线前测试
- 耦合功能变更被波及时
- 集成用例新合入功能验证

#### P1 — 功能完整覆盖（约65%）

```
P1 用例入选标准（满足任一即可标为P1）:

  1. 需求中没有明确要求，但是延伸的功能点
     → 用户可能使用但不是核心路径

  2. 功能的非主路径
     → 该用例如果执行不通过，不影响该功能的其他用例执行

  3. 用例覆盖对应功能的:
     ├── UI界面（布局、样式、交互反馈）
     └── 用户体验维度

  4. 不同版本验证:
     ├── 数据版本
     ├── 不同应用宝版本
     ├── 不同插件版本
     ├── 不同技术框架
     └── SDK版本等
```

#### P2 — 异常与边界（约20%）

```
P2 用例入选标准（满足任一即可标为P2）:

  1. 异常场景:
     ├── 边界值场景（空/超长/最大/最小）
     ├── 频繁操作场景（快速重复点击）
     ├── 网络切换场景（Wi-Fi→有线、弱网→正常）
     ├── 特殊字符输入（XSS/SQL注入/emoji等）
     └── 首启/非首启等非常规操作

  2. 特殊场景:
     ├── 覆盖安装（升级/降级/存量）
     ├── 清数据（清缓存/清存储）
     ├── 杀进程（手动杀/系统杀）
     └── 硬件环境不支持（显卡/内存/磁盘不足等）

  3. 覆盖对应功能的文案等维度
     → 例: 文字展示错误、标点符号、多语言文案
```

### 4.2 优先级分布检查

```
每个用例集编写完成后，自检优先级分布:

  ┌─────────────────────────────────────────────┐
  │  P0:  ████                    ≈ 15%         │
  │  P1:  █████████████████████   ≈ 65%         │
  │  P2:  ████████                ≈ 20%         │
  └─────────────────────────────────────────────┘
  
  ⚠️ 异常信号:
  • P0 > 30%  → 可能过度标记为P0，实际不都是核心路径
  • P0 < 10%  → 核心路径覆盖可能不足
  • P1 < 50%  → 功能覆盖可能不够完整
  • P2 < 10%  → 异常/边界场景覆盖不足
  • P2 > 30%  → 可能有些用例应提升为P1
```

```

  ▼

  │ No
  ▼
页面基本UI渲染? ──Yes──▶ P0
  │ No
  ▼
延伸功能/非主路径? ──Yes──▶ P1
  │ No
  ▼
UI体验/不同版本? ──Yes──▶ P1
  │ No
  ▼
异常/边界/特殊场景? ──Yes──▶ P2
  │ No
  ▼
文案/辅助性检查? ──Yes──▶ P2
```
