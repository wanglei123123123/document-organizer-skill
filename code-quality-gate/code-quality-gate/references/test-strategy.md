# 测试策略生成方法论（Test Strategy Generation）

> 基于**代码变更 + 需求内容 + 耦合场景**三维输入，自动推导并输出一份结构化、可执行的测试策略。
> 目标：让测试人员/AI 在研发提测前就能清楚回答——**测什么、测到什么程度、哪些风险必须覆盖**。

---

### 1.2 生成原则

| 原则 | 说明 |
|------|------|
| **数据驱动** | 所有策略决策必须基于代码 diff、需求条目、调用链等可观测证据，不做主观臆断 |
| **可回溯** | 每一条策略结论都必须标注触发依据（哪段代码/哪条需求/哪个耦合点） |
| **分级输出** | 必测（Must）/建议测（Should）/可选测（May）三级，避免范围失控 |
| **风险优先** | 涉及资金、账号、数据安全、崩溃、升级的变更强制最高优先级 |
| **可执行** | 策略必须能直接转为用例集合（与 `testcase-template.md` 对接） |

## 二、输入采集规范

### 2.1 需求内容采集

**必要字段**（来自 PRD/故事/Figma/图片需求）：

```yaml
requirement:
  id: "REQ-2026-0421-001"
  title: "新增积分中心签到翻倍卡功能"
  type: "new_feature | modify | bugfix | refactor | data_migration"  # 必填
  modules: ["积分中心", "任务系统", "支付"]  # 功能模块
  user_groups: ["新用户", "老用户", "会员"]   # 涉及用户分群
  platforms: ["Android", "iOS", "PC", "H5"]  # 涉及端
  acceptance_criteria:
    - "连续签到7天可领取翻倍卡"
    - "翻倍卡有效期24小时"
  dependencies:
    client_min_version: "8.5.0"   # 若前端能力依赖客户端
    backend_services: ["user-svc", "task-svc"]
    data_migration: true           # 是否涉及数据升级
```

### 2.2 代码变更采集

**必要信息**（来自 git diff / PR）：

```yaml
code_change:
  commit_range: "main..feature/double-card"
  changed_files:
    - path: "src/api/task.ts"
      change_type: "modify"
      added_lines: 42
      deleted_lines: 8
    - path: "src/components/SignIn.tsx"
      change_type: "new"

  changed_modules: ["api/task", "components/SignIn", "utils/reward"]

    - "POST /api/task/sign"     # 接口签名变更
    - "GET /api/reward/list"
  db_schema_change: true           # 是否涉及数据库 schema 变化
  config_change: true              # 是否涉及配置/开关变化
  native_change: false             # 是否涉及客户端原生层
  sdk_change: false                # 是否涉及底层 SDK
```

**必要信息**（来自调用链分析/依赖图）：

```yaml
    - "微信支付"
```

### 3.2 维度二：存量功能影响范围

#### 影响面推导算法

```
影响面 = 直接影响 ∪ 间接影响 ∪ 数据影响 ∪ 共享资源影响
```

| 规则ID | 触发条件 | 回归范围 |
|--------|----------|----------|
| **IMP-01** | 修改了公共函数/工具类 | 所有引用该函数的模块全回归 |
| **IMP-02** | 修改了共享 Store/全局状态 | 所有订阅该状态的页面回归 |
| **IMP-03** | 修改了接口出入参 | 所有调用方回归（前后端联调） |
| **IMP-04** | 修改了数据库 schema | 历史数据读取+新数据写入回归 |
| **IMP-05** | 修改了配置/开关 | 开关开/关两态回归 |
| **IMP-06** | 修改了路由/导航 | 所有入口页面导航回归 |
| **IMP-07** | 修改了权限/登录逻辑 | 所有登录态分支回归（参考 test-methods.md 账号体系） |
| **IMP-08** | 修改了埋点/日志 | 原有埋点事件不丢失验证 |
| **IMP-09** | 修改了支付/结算 | 全部支付链路 + 历史订单查询回归 |
| **IMP-10** | 引入了新依赖包 | 包冲突+首屏性能回归 |

#### 耦合点识别清单

对每个被修改的模块 M，依次回答：

- [ ] 谁调用了 M？（upstream_callers）→ 上游回归
- [ ] M 修改后，调用方是否需要同步修改？→ 前后端联调
- [ ] M 是否读写全局状态？→ 其他状态消费方回归
- [ ] M 是否有定时/事件触发？→ 触发链路回归
- [ ] M 是否被缓存/持久化？→ 升级场景 + 数据清理回归

### 3.3 维度三：兼容性测试决策

#### 触发规则（满足任一必须做兼容性测试）

| 规则ID | 触发条件 | 兼容性测试范围 |
|--------|----------|----------------|
| **COMPAT-01** | 底层代码逻辑变更（SDK/核心工具类/引擎） | 全机型 + 全OS版本矩阵（参考 pcyyb-checklist.md） |
| **COMPAT-02** | 系统 API/接口变更 | 目标 OS 版本 ± 2 个主版本 |
| **COMPAT-03** | 客户端原生层变更（JNI/Swift/OC/C++） | 低端机 + 高端机 + 厂商定制ROM |
| **COMPAT-04** | 渲染引擎/图形相关变更 | OpenGL/Vulkan/DX + NVIDIA/AMD/Intel 三显卡 |
| **COMPAT-05** | 使用新 API（含 iOS 新 API/Android 新 API） | 最低支持版本 OS 回归 |
| **COMPAT-06** | 浏览器 CSS/JS 新特性 | Chrome/Safari/Firefox/Edge + 国内主流内核 |
| **COMPAT-07** | 引入新依赖库（含 gradle/pod/npm 升级） | 依赖冲突 + 包体积 + 启动耗时 |
| **COMPAT-08** | 分辨率/DPI 相关布局变更 | 多分辨率/多DPI 适配回归 |
| **COMPAT-09** | 虚拟化/模拟器场景（PC 类项目） | VBox/Hyper-V/NEMU 三引擎回归 |
| **COMPAT-10** | 多语言/国际化变更 | 至少覆盖 中英 + 一种RTL/长文本语言 |

#### 决策树

```
代码变更 ──┬─▶ 仅修改业务层 JS/TS?  ───▶ 无需专项兼容性测试（常规浏览器/机型抽测即可）
          │
          ├─▶ 涉及 SDK/Native/引擎?  ───▶ 🔴 强制全矩阵兼容性测试
          │
          ├─▶ 使用新系统 API?  ──────▶ 🟠 目标 OS 最低版本必测
          │
          ├─▶ 修改 CSS/布局?  ────────▶ 🟡 多分辨率/DPI 抽测
          │
          └─▶ 仅文案/配置变更?  ──────▶ ⚪ 无需兼容性测试
```

### 3.4 维度四：弱网测试决策

#### 触发规则

| 规则ID | 触发条件 | 弱网测试场景 |
|--------|----------|--------------|
| **NET-01** | 新增/修改网络请求 | 请求级：超时/断网/丢包 |
| **NET-02** | 涉及大文件下载/上传 | 下载暂停/续传/网络切换 |
| **NET-03** | 涉及长连接/WebSocket/推送 | 断连重连/消息不丢失 |
| **NET-04** | 涉及支付/订单关键流程 | 支付中网络中断/订单一致性 |
| **NET-05** | 涉及首屏/关键业务路径 | 2G/3G/弱 4G 下首屏可用性 |
| **NET-06** | 涉及数据同步/云存储 | 网络恢复后同步策略 |
| **NET-07** | 涉及直播/音视频 | 卡顿/降码率/切流 |
| **NET-08** | 涉及离线可用功能 | 完全断网下降级方案 |

#### 弱网场景矩阵

| 场景 | 网络参数 | 适用触发规则 |
|------|----------|--------------|
| 2G | 50Kbps / 500ms 延迟 / 5% 丢包 | NET-01, NET-05 |
| 弱 3G | 200Kbps / 200ms 延迟 / 1% 丢包 | NET-01, NET-02 |
| 延迟网 | 1Mbps / 1000ms 延迟 / 0% 丢包 | NET-03, NET-04 |
| 丢包网 | 5Mbps / 100ms 延迟 / 20% 丢包 | NET-03, NET-07 |
| 间歇性断网 | 断 5s → 连 10s 循环 | NET-03, NET-06 |
| 完全断网 | 0 Kbps | NET-04, NET-08 |
| 网络切换 | WiFi↔4G 切换 | NET-03, NET-07 |

#### 决策规则

```
弱网测试 = 必须 IF:
  - 新增/修改网络请求 AND（请求关键路径 OR 影响用户资金/数据）
弱网测试 = 建议 IF:
  - 新增/修改网络请求 AND 非关键路径
弱网测试 = 不需要 IF:
  - 纯本地计算变更 OR 纯UI样式变更
```

### 3.5 维度五：历史版本验证决策

#### 触发规则

| 规则ID | 触发条件 | 历史版本验证范围 |
|--------|----------|------------------|
| **HIST-01** | 数据库 schema 变更 / 数据迁移 | 老数据读取+升级后数据完整性 |
| **HIST-02** | 前端能力依赖客户端版本 | 低版本客户端降级/提示升级 |
| **HIST-03** | 接口协议新增字段（加字段） | 老客户端调用不报错 |
| **HIST-04** | 接口协议删除/重命名字段（破坏性） | 🔴 强制低版本客户端全回归 |
| **HIST-05** | 本地存储结构变更（localStorage/SP/KV） | 升级后历史数据可读/可迁移 |
| **HIST-06** | 配置/开关默认值变更 | 老用户默认值不变 / 新用户取新值 |
| **HIST-07** | 业务规则变更（如签到规则） | 进行中的老流程按老规则完成 |
| **HIST-08** | 强制升级/热更新变更 | 灰度/回滚路径验证 |
| **HIST-09** | 权限/隐私合规变更 | 老用户授权状态迁移 |
| **HIST-10** | Cookie/Token/登录态结构变更 | 老登录态自动迁移/兼容 |

#### 历史版本矩阵

```
当前发布版本 = N
必测历史版本：
  - N-1 (最近稳定版)            ← 必测
  - N-2 (上上个版本)            ← 建议测
  - N-3 (3 个版本前)            ← 破坏性变更时必测
  - 最低支持版本 (min_version)   ← 必测

数据库历史版本：
  - 当前线上版本 DB schema       ← 必测
  - 上一个版本 DB schema         ← 必测
  - 最老兼容版本 DB schema       ← 数据迁移时必测
```

#### 决策树

```
前端能力依赖客户端? ──是──▶ 🔴 客户端 N-1 / N-2 必测 + 低版本降级提示
数据升级/迁移?       ──是──▶ 🔴 升级前后数据一致性必测
接口破坏性变更?      ──是──▶ 🔴 全历史客户端回归
仅新增字段/功能?     ──是──▶ 🟠 抽测 N-1 不报错即可
纯新功能开关?        ──是──▶ 🟡 验证老用户看不到入口
```

### 3.6 维度六：性能测试决策 ⭐

> 当代码变更或技术方案中涉及新增接口、或可能影响性能的地方时，必须进行性能测试。

#### 触发规则（满足任一须评估性能影响）

| 规则ID | 触发条件 | 性能测试关注点 |
|--------|----------|----------------|
| **PERF-01** | 新增后端接口 / API | 响应时间 P50/P95/P99、QPS、错误率 |
| **PERF-02** | 接口入参/返回数据量显著增加（>2x） | 响应时间劣化、网络带宽、序列化开销 |
| **PERF-03** | 新增/修改数据库查询 | 慢SQL、索引命中、全表扫描、锁等待 |
| **PERF-04** | 循环内 I/O 或循环内调用（N+1 查询） | 循环次数 × 单次耗时放大效应 |
| **PERF-05** | 新增/修改缓存（Redis/本地缓存/CDN） | 缓存命中率、穿透/雪崩、预热策略 |
| **PERF-06** | 大数据量处理（批处理/导出/搜索/推荐） | 内存峰值、GC、处理吞吐 |
| **PERF-07** | 新增/修改首屏/关键路径渲染 | FP/FCP/LCP/TTI、白屏时长 |
| **PERF-08** | 新增动画/复杂渲染/GPU 操作 | FPS、掉帧、GPU 占用、功耗 |
| **PERF-09** | 新增定时/轮询/长连接/后台任务 | CPU 占用、电量消耗、后台唤醒次数 |
| **PERF-10** | 新增大文件读写 / 大量小文件 I/O | 主线程阻塞、磁盘 IOPS、内存占用（联动 STORAGE-10） |
| **PERF-11** | 引入新依赖库 / SDK | 包体积、启动耗时、常驻内存 |
| **PERF-12** | 修改算法复杂度（循环/递归/排序） | 时间复杂度提升风险（O(n²)、O(n³)） |
| **PERF-13** | 涉及并发/锁/线程池 | 吞吐、上下文切换、死锁、锁粒度 |
| **PERF-14** | 多端联调/分布式场景 | 端到端链路时延、跨服务 RT |
| **PERF-15** | 性能敏感业务（支付/直播/游戏/高并发活动） | 全链路压测 + 极限容量 |

## 五、策略生成 Checklist（AI/人工通用）

在输出策略前，AI/测试人员必须逐项回答以下问题：

### 输入完整性
- [ ] 需求类型是否明确（new/modify/bugfix/refactor/data_migration）？
- [ ] 代码 diff 是否可获取（分支对比/PR链接）？
- [ ] 是否识别了所有被修改的模块？
- [ ] 是否识别了上游调用者和下游依赖？

### 新功能维度
- [ ] 是否列出所有新增功能点并关联需求条目？
- [ ] 每个功能点是否有正向+反向+边界+异常四类用例？
- [ ] 是否考虑了用户分群（新/老/VIP）？
- [ ] 是否考虑了登录态（游客/登录/QQ/微信）？

### 存量回归维度
- [ ] 是否识别了所有被影响的存量模块？
- [ ] 共享状态/全局变量的消费方是否都列出？
- [ ] 历史数据读写是否回归？
- [ ] 埋点/日志是否不丢失？

### 兼容性维度
- [ ] 是否判定了是否涉及底层/系统 API/原生层？
- [ ] 兼容性矩阵是否覆盖目标 OS/机型/浏览器？
- [ ] PC 项目是否考虑虚拟化/渲染引擎？
- [ ] 是否考虑多语言/RTL？

### 弱网维度
- [ ] 是否识别了所有网络请求变更？
- [ ] 关键业务路径是否覆盖全套弱网场景？
- [ ] 是否考虑幂等性（断网重试后不重复）？
- [ ] 是否考虑网络切换场景？

### 历史版本维度
- [ ] 是否涉及数据迁移？
- [ ] 前端能力是否依赖客户端版本？
- [ ] 接口变更是否破坏兼容？
- [ ] 本地存储结构是否变更？
- [ ] 低版本降级提示是否设计？

### 性能维度 ⭐
- [ ] 是否新增接口 / 数据库查询 / 缓存？
- [ ] 是否涉及大数据量/循环/递归/算法复杂度变化？
- [ ] 是否修改首屏/关键渲染路径？
- [ ] 是否新增动画/GPU/大文件 I/O？
- [ ] 是否新增定时/轮询/长连接/后台任务？
- [ ] 是否引入新依赖库（包体积/启动耗时）？
- [ ] 性能基线/阈值是否明确（P95/LCP/FPS/内存）？
- [ ] 压测容量是否覆盖业务峰值（含 2~10x）？

## 八、质量门禁

**测试策略本身也需要质量门禁**：

| 检查项 | 要求 |
|--------|------|
| 五维度是否全部决策 | 必须，不允许留空（六维度：新增/存量/兼容/弱网/历史/性能） |
| 每维度决策是否有依据 | 必须标注触发规则ID |
| 是否给出工作量估算 | 必须 |
| 是否给出优先级 | 必须 P0/P1/P2 |
| 是否可追溯（需求ID+commit） | 必须 |

**不合格策略输出示例**（❌）：
> "建议全面测试一下。"

**合格策略输出示例**（✅）：
> "必须进行弱网测试（触发 NET-01, NET-04），覆盖 2G/断网重试/间歇性断网 3 个场景，预计 0.5 人日。"
